VLM 영상 분석 아키텍처 v5.1: 산업안전 CCTV, 업로드·실시간 통합

이 문서가 아키텍처의 단일 기준이다. 서비스·토픽·API·AI 호출·운영 규칙은 여기서 정하고, 기능 spec(docs/specs/)과 계약(service-contracts/)은 이 문서를 세분화한다. 이 문서와 spec·계약이 다르면 먼저 이 문서를 고치고 spec·계약을 맞춘다. 결정의 근거는 ADR(docs/adr/)에 있고, 구현 진행 상태는 handoff에 있다. 이전 문서(legacy/overview.md, 설계 원본 legacy/design-origin-v2.md)는 이 문서로 대체되었다. v5.1은 v5를 구조 재검토한 결과를 반영한 판이다(실시간 Job 소유를 stream-service로, 결정적 carry·상한, 늦은 이벤트를 revision으로). 단계별 상세 표는 처리 흐름, 서비스별 포트·DB·담당은 서비스 카탈로그, 배포·저장은 배포와 데이터 관리에 있다. 같은 폴더의 architecture.html은 이 파일에서 scripts/render-architecture-html.sh로 만든 열람용 사본이다. 이 파일을 고치면 스크립트를 실행해 html을 같이 갱신하고 같은 커밋에 넣는다.

산업현장 CCTV 영상에서 VLM(시각 언어 모델)을 꼭 필요한 순간에만 부르는 두 경로를 둔다. 검색 경로는 영상을 10초 구간으로 잘라 구간마다 이미지 벡터를 만들어 두고, 사용자가 문장으로 장면을 요청하면 벡터로 후보를 찾아 그 시각으로 이동시키고 요청한 대상에 bbox를 그려 보여준다. 이벤트 경로는 탐지기가 지원을 선언한 산업안전 이벤트(쓰러짐, 화재·연기, 보호구 미착용, 물건 제거, 방호 미복구, 위험구역 접근, 장비 방치, 안전시설 이동)의 후보가 나왔을 때만 VLM으로 판정하고, 확정된 결과로 현장의 위험 상태(활성·해소)를 시간순으로 관리한다. 입력은 업로드 파일과 카메라 실시간 스트림 둘이고, 둘은 같은 워커·같은 계약·같은 상태 전이 코드를 거친다.

세 가지가 핵심이다.

  1. stream-ingestor는 "실시간용 chunk-processor"다. chunk-processor와 같은 출력 계약(segment.ready·event.candidate·track.detected·chunk.boundary·chunk.manifest)을 같은 필드로 낸다. 그래서 frame-encoder부터 analysis-api까지는 입력이 청크인지 창인지 모른다.
  2. 상태 전이(위험 활성·해소, 상태 스냅샷, 노출, 재고 변화)는 aggregator 한 곳의 순수 함수 fold로만 계산한다. 업로드는 영상 끝에 한 번, 실시간은 창마다 증분으로 같은 함수를 돌린다. 늦게 도착한 이벤트도 같은 함수로 들어가 결과를 revision을 올려 다시 낸다. 실시간 Job의 소유자는 stream-service이고 pipeline-service는 실시간을 모른다.
  3. 외부 AI는 ai-gateway 한 곳으로만 나간다. 블러 사본만 보내고, 모든 호출은 캐시 → 예산 → 한도 → 출력 검증을 거친다.

2. 설계 원칙

원칙 내용
결과를 날조하지 않음 모델이 설정되지 않았거나 가중치를 못 불러오면 명시적으로 실패한다. 운영 코드에 Mock 경로가 없다. Mock Adapter는 CI·단위 테스트 전용이고 운영 프로필에서 고를 수 없다
탐지기가 능력을 선언 이벤트 후보는 탐지 프로필이 supportedEvents로 선언한 유형에서만 만든다. 선언되지 않은 유형은 결과의 unsupportedEvents에 이유와 함께 남긴다
VLM 출력은 검증 응답은 JSON 키·타입·enum을 검사한다. 근거가 부족하면 unknown·unverified·null을 허용하고 확정값으로 바꾸지 않는다
확정된 것만 상태에 반영 위험 상태와 스냅샷은 confirmed 판정만 바꾼다. 이벤트는 불변 이력, 위험 상태는 현재 상태로 분리한다
정확도를 주장하지 않음 정답 세트가 없으면 지표를 null로 둔다. confidence·similarity를 정확도로 표시하지 않는다. solution과 RAG 답변에는 "안전관리자의 최종 확인이 필요하다"를 붙인다
결정적 ID 구간·후보·트랙·결과·주석 ID와 S3 경로는 uuid5(입력)으로 만들어 재처리·재전달 중복을 흡수한다. 재정규화·재분석은 새 normalizationId·jobId를 받아 같은 산출물로 보지 않는다
계약 우선 레포 경계를 넘는 API·이벤트는 service-contracts/에 먼저 쓰고 구현한다. 다른 담당자가 생산하는 계약은 소비 쪽이 이 문서대로 먼저 쓰고 "생산자 확인 필요"를 남긴다(ADR-0013)
유형·클래스·프롬프트는 데이터 이벤트 유형·트리거 클래스·객체 종류·프롬프트는 코드나 DB enum이 아니라 계약의 버전 파일과 저장소 묶음에서 읽고 기동 시 검증한다. 유형 추가와 프롬프트 변경에 서버 코드 PR이 없다
완료는 적재하는 쪽이 확인 완료 판정은 발행 수가 아니라 적재 완료 신호를 센다. 생산 워커가 내는 manifest는 aggregator가 읽은 수와 다시 맞춰 본다(12절)
모델은 설정으로 교체 모델·프롬프트·탐지 프로필·인코더·기준값은 코드가 아니라 프로필·Registry 값이다. 결과마다 쓴 버전을 기록한다(15절)
블러 사본만 외부 전송 얼굴·번호판을 블러 처리한 사본만 저장·전송한다. ai-gateway는 원본 경로를 거부한다
한 곳에서만 계산 상태 전이·시간 규칙·재고 비교는 aggregator에만 있다. 업로드·실시간이 같은 코드를 쓴다(ADR-0016)

3. 배포 단위 (21개)

Spring 10개는 사용자 요청·업무 상태·저장·조회·품질 검토를 맡고, Python 11개는 영상 디코딩·탐지·추적·벡터·외부 AI 호출을 맡는다. Python 중 ai-gateway만 HTTP 서버이고 나머지는 Kafka 워커다. Quality의 Python 평가 잡은 상주 서비스가 아니라 배포 단위로 세지 않는다.

4. 공통 처리 단위

업로드와 실시간이 같은 워커를 쓰는 근거는 처리 단위를 같은 식별자와 경로 규칙으로 맞춘 것이다. 이 선택으로 계약의 필수 필드(jobId·chunkId·executionId)와 경로 검사(SPEC-019 R-16)를 바꾸지 않고 실시간 입력이 기존 워커를 통과한다.

sourceId (업로드 영상 1개 또는 카메라 세션 1개)
└─ normalizationId (업로드: 불변 정규화 사본 · 실시간: 세션 ID 재사용)
   └─ jobId (FULL · REANALYZE · REEMBED · STREAM)
      └─ chunkId (업로드: 청크 2분 · 실시간: 창 20초, 순번)
         ├─ executionId (실행 시도마다 새 ID)
         └─ segmentId · candidateId · trackLocalId · eventId (uuid5, 청크·창 경계와 무관)
개념 업로드 실시간 계약
소스 업로드 영상 1개 카메라 1대의 수집 세션 1개. stream-service가 start 때 sourceId를 발급하고 stop 때 닫는다. 24시간마다 새 세션으로 회전하고 previousSourceId로 상태를 잇는다 모든 봉투의 sourceId
Job FULL·REANALYZE·REEMBED. pipeline-service 소유. 청크 수가 계획 때 정해지고 끝이 있다 STREAM. stream-service 소유. 창 수가 미리 정해지지 않고 stop 또는 24시간까지 열려 있다 analysis.completed.jobType, 산출물 토픽의 jobType(없으면 FULL)
청크·창 2분(10분 미만 영상 1분, 2시간 초과 3분) + 앞뒤 5초 20초(프로필, 10~30초) + 앞뒤 5초. Ingestor가 순번으로 chunkId를 발급 chunkId, ownedRange, processingRange
실행 pipeline-service 배정기가 executionId 발급, 슬롯 점유 Ingestor가 창마다 발급. 슬롯 개념 없음(카메라 1대 = Pod 1개) executionId

읽을 때 기억할 것이다.

  • 모델이 워커 안에서 도는 단계(4, 5, 8)는 ai-gateway를 부르지 않는다. 외부 AI 비용은 7, 10, 11, 13에서만 생긴다.
  • 판정 결과의 verificationStatus는 넷이다. confirmed·rejected는 모델 판정, unverified는 모델 미설정·예산 초과·호출 상한, unknown은 출력 검증 실패·호출 실패다. 상태 전이는 confirmed만 쓴다.
  • Normalize는 재인코딩이 필요한 영상에서 첫 청크 시작을 영상 길이만큼 늦춘다. SLO "업로드 후 첫 결과까지"는 복사 경로와 재인코딩 경로를 나눠 잰다. 재인코딩 영상 비율을 측정한 뒤 청크별 재인코딩으로 바꿀지 정한다(검토 H, 기본안 D-5).

6. 실시간 경로

카메라 1대의 수집 세션 1개가 소스가 되고, stream-ingestor가 창(기본 20초)마다 chunk-processor와 같은 산출물을 낸다. 창 이후는 5절의 5~11단계와 같은 워커가 같은 메시지를 처리한다. 다른 점은 넷이다. (1) STREAM Job의 생명주기·창 단위 완료 판정·라이브 읽기 모델은 pipeline-service·analysis-api가 아니라 stream-service가 맡는다. (2) aggregator는 analysis-api를 읽지 않고 Kafka 입력만으로 창마다 증분 fold한다. (3) severity high 유형과 활성 위험 구역 접근은 창 종료를 기다리지 않고 alert.candidate로 먼저 나간다. (4) track-stitcher는 쓰지 않는다. 다른 담당자 서비스는 기존 소비 그대로이고, 요구는 11.4절의 네 줄뿐이다.

Job과 완료 판정 stream-service가 STREAM Job을 자기 DB에 등록한다. 창마다 segment.indexed(search-service)와 event.manifest(event-analyzer)가 모이면 analysis.completed(scope: chunk)를 내고, stop 뒤 마지막 창(chunk.manifest.last)까지 모이면 scope: job을 낸다. pipeline-service는 STREAM을 모른다

세션 길이 최대 길이(프로필, 기본 24시간)를 넘으면 stream-service가 세션을 닫고 새 세션(새 sourceId)을 연다. 새 세션의 초기 상태는 직전 세션의 마지막 상태다(previousSourceId, 작업 세션과 같은 장치). 창 수·벡터·결과 파일이 세션 단위로 유한해진다

녹화 재생용 HLS 조각 6초(sources/<sourceId>/live/hls/, 보존 24시간), 보관용 창 파일(sources/<sourceId>/live/<chunkId>.mp4, 보존 7일). 근거 프레임은 업로드와 같은 실행 경로 아래 블러 사본(blurred/f<ptsMs>.jpg)

라이브 읽기 모델 stream-service가 event.analyzed(이벤트 요약), state.updated(위험·스냅샷·노출), alert.raised(알림)를 소비해 세션 동안의 타임라인·상태·알림을 저장하고 GET /api/v1/stream/sessions/{id}/state · events · alerts로 준다. 세션이 닫히면 source.completed로 analysis-api가 보관 결과(활성 버전)를 갖고, stream-service의 라이브 행은 보존 기간(7일) 뒤 지운다

중복 비용 같은 입력 해시·taskType·버전이라 ai-gateway 결과 캐시(SPEC-016 R-2)가 적중한다. dismissed(rejected)도 캐시되어 창 판정이 같은 결과를 낸다
지연 목표 탐지 1초 미만 + 1차 알림 2초 이내, VLM 확정까지 2~5초(추정). 실측은 stage.timing의 ingest.alert·analyzer.judge로 잰다
알림 상태 pending → confirmed 또는 dismissed. 화면은 pending을 "확인 중"으로 보이고, dismissed는 접는다. stream-service가 알림 이력을 저장한다

1 질의 해석 규칙 사전이 먼저 처리한다. 시간·상태 표현("이후", "남은", "현재 위험")으로 video_retrieval·temporal_video_rag를 나누고, 한국어 → 영어 시각 대상어 사전(안전모 미착용 → person without a hard hat)으로 대상어 1~3개를 뽑는다. 사전에 없으면 query_parse로 보조하고, 그래도 없으면 person으로 제한한다. 결과에 해석 방법(industrial-rule·english-phrase·llm·safe-fallback)을 표시한다(SPEC-012) query_parse(luna, 사전 밖만)
2 재사용 확인 표준 질의 키로 저장된 결과가 있으면 바로 돌려준다 없음
3 시각 검색 영어 검색 문장을 활성 인코더의 텍스트 타워로 벡터화해 활성 버전·권한 범위의 구간 벡터에서 top-50. 5초 겹치는 인접 구간은 점수 높은 쪽만 남긴다 embed_visual_text(외부 비용 없음)
4 텍스트 검색 질의 텍스트 벡터와 pg_trgm 키워드 검색을 RRF로 합친다. 이벤트 유형·속성·시간 조건은 필터다 embed_text
5 정밀 검색(선택) precise=true일 때만 상위 10구간 대표 프레임을 segment_rerank로 한 번에 보낸다. 기준 점수 미만이면 "찾지 못함" segment_rerank(terra, luna 옵션)
6 결합·이동 시각·텍스트 결과를 RRF로 합치고 결과마다 이동 시각(시작 2초 전)·유사도·인코더·해석 방법을 돌려준다. 점수는 "유사도"로만 표시한다 없음

8 저장 결과·판정·클립 경로를 저장하고, 신뢰도 높은 판정은 구간 주석으로 segment.annotated 없음

이미지로 장면 찾기는 /v1/embed(이미지 모드)로 벡터를 만들어 구간 벡터와 크롭 벡터 양쪽에서 찾는다. 질의 이미지는 queries/<queryId>/ 경로만 ai-gateway가 받는다.

규칙 내용
인코더 일치 구간 벡터(frame-encoder)와 질의 벡터(ai-gateway)는 같은 인코더 모델 ID여야 한다. 벡터마다 embeddingModel을 기록하고 같은 모델 벡터만 검색한다
데이터 조건 segment_vector에 (source_id, analysis_version, embedding_model) B-tree가 반드시 있어야 한다. 영상 하나나 영상 범위를 거는 검색은 플래너가 B-tree로 후보를 추리고 정확히 정렬한다(실측 108,000행에서 영상 1개 0.3ms, 영상 75개 20ms). B-tree가 없으면 HNSW가 필터를 걸고 0행을 돌려준 사례가 있다(14절)

프레임 평균의 한계 구간 벡터에 움직임 정보가 없다. 행동 질의는 이벤트 텍스트 인덱스로 보완하고 화면에 "장면 외형 기준 검색"을 표시한다
지연·장애 ai-gateway 호출이 타임아웃(5~8초)을 넘기면 인코더 순위로 응답하고, 서킷이 열리면 재순위화 없이 응답한다. RAG는 15초를 넘기면 답변 null과 근거만 돌려준다
상한 사용자별 분당·일별 정밀 검색·RAG 횟수에 상한을 두고 넘으면 인코더 순위만 돌려준다
질의 로그 질의, 해석 방법, 결과, 실제 이동·재생 구간, 맞음·틀림을 기록해 사전 보강과 Golden Set 질의 후보로 쓴다

7.1 Video RAG

GET /api/v1/search/sources/{id}/answer?q=로 질문을 받으면 search-service가 근거를 모으고 VLM이 근거만으로 답한다.

단계 서비스 내용
1 search-service 질의 해석. 이 엔드포인트로 오면 route와 상관없이 RAG로 처리
2 search-service 시각 검색 top-k(기본 5)로 근거 구간과 대표 프레임 경로를 모은다
3 search-service → analysis-api 내부 읽기 이벤트(설명문·위험 사유·조치 제안), 상태 스냅샷, 활성·해소 위험 상태. 이벤트는 질문 어휘 겹침 점수와 텍스트 인덱스 점수를 RRF로 합쳐 상위 k개만
4 search-service → ai-gateway video_rag(luna): 질문 + 근거 구간 프레임 + 이벤트·상태·위험 JSON, "근거에서만 답하고 불확실하면 명시" 지시
5 search-service 답변, 상태(confirmed·unverified), 근거 구간(이동 시각), 관련 이벤트, 제한 사항. VLM 미설정·타임아웃이면 답변 null과 근거만
6 search-service 표준 질의 + sourceId + 분석 버전 + 모델·프롬프트 버전 키로 저장

7.2 결과 재사용

비싼 결과는 DB에 영구 저장하고 Redis는 앞단 캐시로만 쓴다. 키는 원문이 아니라 규칙 사전이 만든 표준 질의다. LLM 보조로 해석된 질의는 temperature 0과 모델 스냅샷 고정으로 재현성을 맞추고, 키에 해석 방법과 사전 버전을 넣는다. 의미 유사도 캐시는 쓰지 않는다.

단계 재사용 키 저장
질의 해석 정규화 문장 + 사전 버전 + query_parse 프롬프트 버전 Redis → DB
질의 벡터 표준 질의 + embeddingModel Redis → DB
후보 검색 표준 질의 + sourceId + 분석 버전 + embeddingModel Redis(짧은 TTL)
정밀 검색 결과 표준 질의 + sourceId + 분석 버전 + 재순위화 모델·프롬프트 버전 DB 영구 + Redis
구간별 판정 segmentId + 표준 질의 + 재순위화 버전 DB
주석 클립 groundingId = (대상어, segmentId, grounding 모델) DB 경로 + S3
RAG 답변 표준 질의 + sourceId + 분석 버전 + 모델·프롬프트 버전 DB 영구 + Redis
구간 주석 segmentId(출처 질의·판정 버전 기록) DB + 텍스트 임베딩

활성 분석 버전·인코더·모델·프롬프트·사전이 바뀌면 키가 달라져 자동으로 분리된다. STREAM 소스는 적재가 계속되므로 후보 검색 캐시 TTL을 창 길이 이하로 둔다. "틀림" 피드백이 오면 해당 결과와 주석을 무효화한다.

7.3 지연 목표

기본 검색(정밀 검색 없음)은 규칙 사전 해석 수 ms + 질의 벡터 수십 ms + 벡터 검색 수십 ms로 1초 안팎을 목표로 한다. bbox 주석은 비동기라 응답을 막지 않는다. 정밀 검색은 VLM 재순위화가 더해져 2~5초로 추정하고 PoC에서 p50·p95를 잰다. 목표를 넘으면 두 번 나눠 응답, 후보 축소, 저해상도 입력, 조건부 재순위화, 응답 후 백그라운드 재순위화, 인기 질의 사전 계산을 순서대로 검토한다.

hazard_zone_access 위험구역 접근 hazard_zone_person(구역 안 사람) 활성 위험 상태 또는 구역 정의 구역 진입은 규칙 확정, 체류·배회는 aggregator, 활성 위험 중 접근은 aggregator가 VLM medium(활성 위험 중이면 high) 활성 위험 중이면 예 120초
equipment_abandoned 장비 방치 장비 트랙이 사람 없이 N분(기본 10분) 정지(aggregator 시간 규칙의 가상 클래스) 장비 클래스, 트랙, 구역 정의 템플릿. 통로·위험구역이면 VLM medium 아니오 없음
object_moved 안전시설 이동 같은 클래스의 제거·등장이 시간 창(120초) 안에서 짝지어짐(aggregator 재고 비교) 정적 객체 재고(chunk.manifest), 구역 정의 VLM state_compare medium 아니오 없음

최소 관측 수는 모두 2다. 목록 밖 사건은 other와 자유 설명으로 받고 검색 경로로 찾을 수 있게 둔다. 구역이 전제인 이벤트는 구역이 정의되지 않은 소스에서 unsupportedEvents에 "구역 정의 없음"으로 남고, 구역을 나중에 정의하면 REANALYZE로 다시 돌린다(실시간은 다음 창부터 적용). 재판정 간격은 상태형 유형에서 같은 (sourceId, trackId, 유형)의 마지막 confirmed 뒤 그 시간 안에는 VLM을 부르지 않고 이전 결과를 잇는 값이다. 업로드는 트랙 ID가 청크 로컬이라 같은 값을 메시지 안 구간 규칙으로 적용한다(기본안 D-9, AI 담당자가 Golden Set으로 조정).

8.3 탐지기와 능력 선언

탐지 프로필(taxonomy/v2/detector-profile.schema.json)에 탐지기 구성(가중치 manifest 경로·클래스), 프로필 버전·학습 출처·체크섬과 supportedEvents를 적고, 기동 시 검증한 뒤 결과마다 프로필 버전을 기록한다. 선언되지 않은 유형은 unsupportedEvents: {유형: 이유}로 남고 analysis-api가 요약에 "이 분석에서 판정하지 않은 이벤트"로 표시한다.

YOLO26n(COCO) 없음 추적·구역 규칙·클릭 조회·재고의 기본

8.4 판정 규칙

이벤트 종류 판정
구역 진입 chunk-processor·stream-ingestor가 규칙으로 확정, 템플릿 설명(VLM 없음)
체류·배회 등 시간 기준 aggregator가 경계를 이은 트랙으로 판단(체류 60초, 배회 3회/300초), 템플릿 설명
쓰러짐·화재·보호구·물건 제거·방호 미복구 event_judge 1회로 VLMAnalysis
결과가 severity high이거나 eventDetected null event_judge_escalate로 재판정, 두 판정이 다르면 reviewRequired. 기본 severity high 유형은 모델이 그대로 내면 2회 호출이 된다(17절)
같은 트랙·같은 유형 반복 메시지 안에서 앞 후보 끝과 다음 후보 시작 간격이 10초 이하면 이어 붙여 confidence 최대 1개(mergedCandidateIds). 청크·창 경계는 aggregator가 판정 뒤 병합
상태형 유형 반복 업로드: 메시지 안에서 같은 (trackLocalId, 유형) 후보를 시작순으로 놓고 간격(120초)마다 첫 후보만 판정, 나머지는 결과를 복사해 judgmentMethod: rule+carry. 실시간: Redis의 마지막 confirmed 시각이 간격 안이면 같은 방식. 공유 상태가 없거나 창 순서가 보장되므로 결정적이다
실행당 호출 상한 max(3, 분당 3회 × 실행 길이)(2분 청크 6회, 20초 창 3회). 넘으면 호출 없이 unverified, unverifiedReason: call_cap_reached. 공유 카운터 없이 Job 합이 상한 이하다(기본안 D-10)
벡터 후보 event_judge로 판정, vector+vlm. high이거나 판단 불가면 escalate(vector+vlm+escalate). 트랙이 없어 쿨다운 병합은 없고 frame-encoder의 연속 구간 병합이 상한이다
긴급 후보 alert.raised(pending)를 먼저 내고 event_judge로 confirmed·dismissed를 낸다. 이벤트는 같은 candidateId의 창 후보가 캐시 적중으로 저장한다(rule+vlm). 긴급 경로는 이벤트를 저장하지 않는다
활성 위험 중 접근 aggregator fold가 hazard_zone_access 규칙 이벤트와 활성 위험 구간의 겹침을 보고 트랙 대표 프레임으로 event_judge. Job당 20회 상한에 센다
장비 방치 aggregator 시간 규칙, 템플릿. 통로·위험구역이면 event_judge
재고 변화(제거·등장·이동·미복구) aggregator가 전후 구간 대표 프레임으로 state_compare, Job당 20회 상한
예산 초과 ai-gateway가 unverified(unverifiedReason: budget_exceeded). 재판정하지 않고 발행하고 완료는 정상 진행된다. quality-service가 event.analyzed로 운영자 재판정 큐를 만든다(17.3절)

판정 방식(judgmentMethod)은 rule, rule+carry, rule+vlm, rule+vlm+escalate, vector+vlm, vector+vlm+escalate다. 접두 rule은 탐지기 후보에서 나온 것이고 완료 판정과 개수 검증은 이 접두만 센다. unverified에는 unverifiedReason(budget_exceeded·model_unavailable·call_cap_reached)을 붙인다.

9. 상태 전이와 위험 상태

이벤트는 청크·창 단위로 병렬 판정되므로 판정 시점에는 "직전 상태"가 없다. 상태 전이는 aggregator가 fold 한 함수로만 계산한다. 업로드·실시간·늦은 이벤트가 모두 같은 함수를 지난다.

9.1 fold 정의

fold(state, events[]) → state'에서 state는 구역별 현재 상태 스냅샷, 활성 위험 목록, 노출 누적, 정적 객체 재고, 진행 중인 시간 규칙(체류·배회·방치 타이머)이다. events는 confirmed 이벤트를 evidenceEnd 오름차순(같으면 eventId 순)으로 정렬한 것이다. 같은 입력이면 같은 결과를 내는 순수 함수이고, 상태 재구성은 빈 상태에서 전체 이벤트를 다시 fold해 얻는다.

호출 시점 초기 상태 입력 이벤트 출력
업로드 analysis.completed(scope: job) 빈 상태, 세션이 있으면 직전 영상의 마지막 상태 읽기 API로 읽은 Job 이벤트 전체 중 confirmed(rule*·vector* 모두) + Redis 대기 집합의 벡터 이벤트 + fold 안에서 만든 규칙 이벤트. 개수 대조는 rule*만 source.completed(revision 1, 결과 파일)
실시간 analysis.completed(scope: chunk) Redis의 세션 현재 상태(없으면 S3 스냅샷, 없으면 직전 세션 마지막 상태, 없으면 빈 상태) Redis 대기 집합에 모아 둔 그 창의 confirmed 이벤트. 개수 대조는 rule*만 state.updated 1건(sequence, 증분)
늦은 벡터 이벤트(업로드) 그 Job의 마지막 상태 완료 뒤 도착한 vector* confirmed 이벤트 1건. 결과 파일의 입력 eventId 집합에 없을 때만 그 시각 이후를 다시 fold해 source.completed를 revision + 1로 다시 낸다. 결과 파일 경로는 같고 내용이 바뀐다
늦은 벡터 이벤트(실시간) 세션 현재 상태 창 fold 뒤 도착한 vector* confirmed 이벤트 다음 state.updated에 포함
REANALYZE use_previous_state면 이전 분석 버전의 스냅샷 새 Job의 확정 이벤트 새 분석 버전의 source.completed

aggregator는 모든 Job의 event.analyzed를 소비한다. 업로드 Job이 아직 완료되지 않았으면 vector* 이벤트를 Redis 대기 집합 pending-vector:<jobId>(TTL 7일)에 두고, 완료 fold 때 읽기 API 결과와 합친다(eventId로 중복 제거). 이렇게 하면 읽기 시점과 도착 시점 사이에 끼인 이벤트를 잃지 않는다. 실시간 Job은 event.analyzed·track.detected를 pending:<sourceId>:<chunkId>에 모은다.

9.2 위험 상태와 스냅샷

항목 내용
입력 confirmed 이벤트만. 나머지는 이력에 남지만 상태를 바꾸지 않는다
상태 스냅샷(analysis.state_snapshot) snapshotId, sourceId, zoneId(구역 없으면 global), timestamp(= evidenceEnd 또는 후보 end), 이전·현재 상태, 판정 상태, relatedEventId. 불변 이력

활성 전이 riskDetected=true + riskType + riskReason → 같은 구역·유형의 활성 상태가 있으면 lastSeen·관련 이벤트 갱신, 없으면 새로 활성

재현성 분석 버전마다 따로 저장한다. 업로드는 source.completed.revision, 실시간은 state.updated.sequence로 순서를 지킨다. 소비자는 작은 번호를 버린다

9.3 늦은 이벤트

완료 판정 뒤에 저장되는 이벤트는 벡터 후보 판정 하나다(긴급 후보는 알림만 만들고 창 후보로 저장되며, 재판정은 새 분석 버전이다). aggregator가 event.analyzed를 직접 받아 9.1대로 처리하므로 analysis-api는 새 토픽을 내지 않는다. 업로드는 source.completed를 revision을 올려 다시 내고, analysis-api는 결정적 ID로 upsert한다(생산자 확인 필요: 같은 jobId의 재전달에서 내용이 바뀔 수 있다). 운영자 검토로 confirmed가 된 이벤트를 상태에 반영하는 것은 이후 범위다(ADR-0016).

11. 통신 규칙

11.1 규칙

구분 규칙
외부 → 내부 frontend → api-gateway만 공개한다. 각 서비스는 클러스터 내부(ClusterIP)에서만 접근한다. 카메라 RTSP는 stream-ingestor가 내부망에서 당겨온다
인증 api-gateway가 JWKS로 JWT를 검증하고 사용자 ID와 역할을 헤더로 전달한다. 클라이언트가 보낸 같은 이름의 헤더는 지운다. 각 서비스는 인가만 한다
서비스 ↔︎ 서비스 상태 변경은 Kafka 이벤트로만 전달한다(ADR-0002). 내부 읽기 전용 API는 허용한다(aggregator·search-service → analysis-api, api-gateway → auth-service JWKS). 읽기 API는 호출하는 쪽이 없어도 제공하는 쪽이 동작한다
내부 동기 호출 HTTP/1.1 + JSON. gRPC는 측정상 모델 시간을 포함하면 차이가 1% 미만이라 채택하지 않았다. 계약은 service-contracts/openapi/에 두고 Java·Python 클라이언트는 빌드 때 생성한다. 호출자는 X-Request-Deadline(epoch ms)을 넣고 받는 쪽은 남은 시간을 자기 타임아웃과 하위 호출에 넘기며, 남은 시간이 없으면 504로 답한다. 오류는 Problem Details(RFC 9457)다(SPEC-021)
재시도 읽기 전용 호출(parse, embed, analysis-api 읽기)만 503·연결 실패에 지수 백오프로 2회 재시도한다. analyze(VLM)는 요청이 도착하지 않은 연결 실패만 재시도하고 502·503·시간 초과는 재시도하지 않는다. 호출한 쪽은 unknown으로 기록하고 재판정 Job이 다시 본다
시작 신호 같은 작업을 시작시키는 신호가 여러 개여도 하나의 조건부 상태 전이로 모은다
파티션 키 모든 토픽의 키는 봉투의 sourceId다. 같은 소스의 메시지는 한 파티션에서 순서대로 온다. 실시간은 카메라 세션 = 소스라 창 순서가 지켜진다
대량 데이터 구간 목록, 벡터, 검출 박스, 후보 256개 초과분은 S3 파일로 두고 이벤트에는 경로와 개수만 싣는다
완료는 적재하는 쪽이 확인 pipeline-service는 생산 신호(segment.embedded)가 아니라 적재 신호(segment.indexed)를 센다. 생산 워커가 내는 manifest(event.manifest·track.manifest)는 aggregator가 읽은 수와 다시 맞춘다
순서 상태 전체를 담은 이벤트(version.activated, job.status, state.updated)는 단조 증가 순번을 실어 소비자가 오래된 것을 버린다. 각각 처리해야 하는 이벤트(video.uploaded·deleted, event.analyzed, track.detected)는 버리지 않고 조건부 전이와 삭제 흔적으로 순서를 다룬다
데이터 공유 필터링과 권한 판단에 쓰는 최소 필드만 이벤트로 복제한다. 봉투에 ownerId(JWT sub)와 producedAt을 싣는다
계약·재시도 토픽 JSON Schema 계약 테스트, 필드는 추가만 허용한다. 소비 그룹별 retry 토픽(지수 백오프 + 지터), 상한 뒤 DLQ, eventId로 중복을 흡수한다
외부 AI 전송 이미지를 외부로 보내는 지점은 ai-gateway 하나이고 블러 사본 경로만 받는다
서비스 디스커버리 Kubernetes Service DNS(로컬은 compose 서비스 이름). 별도 레지스트리는 쓰지 않는다

늦은 이벤트 aggregator가 source.completed를 revision + 1로 다시 낸다 다음 state.updated에 포함

13. 여러 Pod 운영

모든 서비스는 여러 Pod로 실행된다는 전제로 설계한다. Pod 메모리에는 공유 상태를 두지 않는다. stream-ingestor만 예외로 카메라별 추적 상태를 메모리에 두되, 임대와 trackIdEpoch로 재시작을 흡수한다.

규칙 내용
상태 위치 공유 상태는 DB·Redis·S3에만 둔다. Pod 메모리는 캐시, 묶음 처리 버퍼, 로드한 모델, Ingestor 추적 상태로만 쓴다
중복 실행 방지 조건부 상태 전이, FOR UPDATE SKIP LOCKED, Redis 원자 연산(SET NX·Lua) 중 하나로 한 Pod만 성공하게 한다
멱등 구간·후보·트랙·결과·주석 ID와 S3 경로는 결정적이다. 소비자는 eventId로 중복을 흡수하고, 일괄 적재(analysis-loader·search-service)는 임시 테이블에 COPY한 뒤 고유 키로 upsert한다
Outbox 발행기 ID 순 행 단위 FOR UPDATE SKIP LOCKED. Publisher는 배정·슬롯 점유를 하지 않는다
주기 작업 타임아웃 처리, 완료 점검기, 정리 작업은 행 잠금이나 분산 락으로 한 Pod만 실행한다
긴 처리 chunk-processor·normalize·event-analyzer·grounding-worker는 pause/resume으로 처리하고 메인 루프는 poll을 계속 불러 재배치에 바로 응답한다. 재배치는 cooperative-sticky다
종료 신호 SIGTERM이 오면 진행 중 작업을 커밋하지 않은 채 소비 그룹에서 나간다. Ingestor는 진행 중 창을 마감해 발행한 뒤 임대를 놓는다
커넥션·메모리 Spring 커넥션 풀 × 최대 Pod 수의 합을 RDS 최대 커넥션 안에 둔다. 모델을 올리는 워커(frame-encoder, ai-gateway, chunk-processor, stream-ingestor, grounding-worker)는 최대 Pod 수 × 모델 메모리를 노드 용량에 반영한다
서비스 장치
pipeline-service 완료 판정은 job 행을 FOR UPDATE로 잠근 트랜잭션 안에서 진행 기록 삽입, 개수 비교, 조건부 전이, Outbox 삽입을 한 번에 한다
stream-service 창 완료는 (session, chunkId) 행 단위로 pipeline-service와 같은 방식이다. 세션 start·stop·24시간 회전은 세션 행 조건부 전이이고 회전 점검기는 행 잠금으로 한 Pod만 돈다. state.updated는 sequence가 저장된 값보다 클 때만 적용한다
stream-ingestor 카메라 임대는 Redis SET NX + TTL 30초, 10초 갱신. 임대 없는 Pod는 명령을 무시한다. 임대를 이어받은 Pod는 trackIdEpoch를 올려 이전 ID와 겹치지 않는다. stop·reload·활성 위험 구역은 Redis 세션 키를 창마다 읽는다
analysis-api 활성 버전 전환은 버전 행 잠금 안에서 "source.completed 수신 + 저장 수 = manifest 수"일 때만 한다. revision이 저장된 값보다 작은 source.completed는 버린다
search-service 같은 표준 질의의 정밀 검색·RAG가 동시에 오면 Redis 락으로 한 Pod만 모델을 부르고 나머지는 결과를 기다린다
ai-gateway 같은 입력(입력 해시 + taskType + 버전)은 Redis single-flight로 한 Pod만 모델을 부른다. 예산은 호출 전에 원자적으로 예약하고 보내지 못하면 되돌린다. Redis가 없으면 single-flight는 생략하고 분당 한도는 Pod별로 지킨다
event-analyzer 후보를 실행당 한 건으로 받아 기다리는 단계를 없앤다. 후보 단위로 재시도하고 끝까지 실패한 후보만 unknown. 모든 후보를 확정한 뒤 오프셋을 커밋한다. 구간 규칙·실행당 상한은 메시지 안에서 계산해 공유 상태가 없고, 실시간 재판정 간격만 Redis 원자 연산이다
track-stitcher 짝 없는 트랙의 타임아웃은 한 Pod가 주기적으로 확인하고 확정 권한은 Redis에서 원자적으로 한 Pod만 가져간다
grounding-worker groundingId가 결정적이라 같은 요청이 두 번 와도 S3에 클립이 있으면 건너뛴다
aggregator 소스 하나는 한 Pod가 처리한다(sourceId 키). fold는 순수 함수라 재실행해도 같다. 실시간 상태는 Redis(핫) + S3 스냅샷(30창마다)이고, 둘 다 없으면 analysis-api 읽기 API로 세션 이벤트를 다시 읽어 재구성한다. 업로드의 벡터 대기 집합은 Redis SADD로 모은다
quality-service 검토 큐 할당은 조건부 갱신(UNASSIGNED → ASSIGNED). 평가 잡은 Golden Set 버전을 고정해 실행한다
notification-service Redis pub/sub으로 모든 Pod에 전달하고 사용자별 Redis Stream에 최근 이벤트를 남겨 다른 Pod로 다시 연결해도 Last-Event-ID 이후를 보낸다. alert.raised는 별도 채널로 먼저 보낸다
auth-service 재발급 토큰 회전은 "아직 쓰지 않은 토큰일 때만" 조건부 갱신, 알림 티켓은 Redis GETDEL로 한 번만 쓴다

14.1 pgvector 조건

필터가 붙은 벡터 검색은 B-tree가 있어야 맞게 동작한다. pgvector 0.8.7, halfvec(512), 코사인, 150개 소스 × 720구간 = 108,000행으로 실측한 결과다.

질의 플랜 반환 행 실행 시간
source_id = 7 top-50, B-tree 있음 B-tree 비트맵 스캔 720행 + 정렬 50(정확 스캔과 50/50 일치) 0.32ms
필터 없음 top-50 HNSW 인덱스 스캔 50 0.32ms
소스 75개 범위 필터 B-tree 54,000행 + 정렬 50 19.5ms
소스 10개 범위 필터 B-tree 7,200행 + 정렬 50 2.3ms
source_id = 7, B-tree 삭제 후 HNSW 스캔 + 필터, 391행 걸러짐 0 0.10ms

따라서 (1) segment_vector·crop_vector에 (source_id, analysis_version, embedding_model) B-tree를 스키마 조건으로 둔다. (2) 소스 하나·소스 범위 검색은 B-tree를 타는 플랜을 기대하고, 전체 검색만 HNSW를 쓴다. (3) 플랜이 바뀌면 재현율이 0이 될 수 있으므로 search-service 계약 테스트에 "필터 검색 반환 행 = 50"을 둔다. search-service는 다른 담당자라 이 조건은 "생산자 확인 필요"다.

14.2 삭제와 보존

  • 소스 삭제(video.deleted)를 모든 서비스가 받아 자기 데이터를 지우고, S3는 sources/<sourceId>/ 접두사로 지운다. 실시간 세션도 같은 토픽이다.
  • 보존 등급은 ADR-0011을 따른다. (a) 영상·프레임·크롭·벡터·모델 원문·자유 문장은 바로 지우고, (b) 비식별 파생 데이터는 동의한 소스만 보존 키로 바꿔 1년 둔다.
  • 모델 가중치, Prompt Registry 묶음, Golden Set은 소스 삭제와 관계없다.

16. 품질 검증

항목 내용
Golden Set 확정 버전은 S3(Versioning·Object Lock), 작업 중 라벨·평가 결과는 quality DB. 라벨은 bbox 검출, 시간 구간 이벤트(8종 + other, 근거 프레임 포함), 상태 변화, (질의, 정답 구간) 세트. 소스 단위로 개발·평가 세트를 나눈다. 조정(프롬프트, 경계값, 정밀 검색 K, YOLOE 클래스, 재판정 간격)은 개발 세트로만, CI Gate와 보고는 평가 세트로만 한다(SPEC-029, SPEC-030)
검토 큐 reviewRequired 이벤트, 긴급 알림의 dismissed, "없음" 판정 구간의 무작위 표본, 예산 초과 unverified를 큐에 넣는다. 큐의 사유는 event.analyzed의 reviewRequired·unverifiedReason에서 온다. 운영자의 확인·기각은 라벨 후보가 된다. 검토로 confirmed가 된 이벤트를 상태에 반영하는 것은 이후 범위다(9.3절)
평가 실행 데이터셋·분류 체계·프로필·모델 버전을 고정해 실행한다. 호출자 quality-eval로 ai-gateway를 부르고 운영 예산과 분리된 하루 한도를 쓴다
CI Gate 후보 재현율, 판정 정밀도·재현율, 상태 전이 정확도, 검색 Recall@50·nDCG@10, 단계 p95 기준선 대비 비율. 기준 미달이면 실패한다
측정 항목 후보 재현율(탐지 프로필별), 판정 정밀도·재현율과 unknown·unverified 비율, 상태 전이 정확도(라벨된 활성·해소 시각과 fold 결과 비교), 검색(Recall@50, 첫 결과 적중률, nDCG@10, 정밀 검색 후 적중률, "찾지 못함" 정확도, 해석 방법별 분리), 긴급 알림 지연(alert.candidate 발행부터 1차 알림까지)과 dismissed 비율, 인코더 비교(MobileCLIP2-S0 vs 대체 모델)
처리 단계 측정 단계 ID <서비스>.<동작>(service-contracts/stages/). 공통 메시징 라이브러리가 핸들러마다 queue_wait(브로커 timestamp 기준)·handle을 재고 stage.timing으로 보낸다. quality-service가 소스별 단계 분해, 단계별 p50·p95 추이, 프로필·모델 버전별 비교 리포트를 낸다. v5 단계 ID: ingest.window, ingest.alert, aggregate.fold(SPEC-013)
정직성 정답이 없는 항목은 null. 운영 화면에는 Golden Set으로 잰 지표만 표시한다. 로컬(Ollama) 판정 결과로 품질을 판단하지 않는다

17. 비용

외부 AI 비용은 ai-gateway를 부르는 단계에서만 생긴다. 워커 안 모델(YOLO, MobileCLIP2)은 CPU 노드 비용만 든다. 단가는 설계 원본의 추정(event_judge 1회 ≈ $0.0023, 환율 1,330원)을 쓰고 PoC에서 usage로 보정한다. 실시간은 외부 AI보다 CPU와 S3 요청 비용이 10배 이상 크다(17.4절).

17.3 예산을 넘었을 때

ai-gateway는 모델을 부르지 않고 unverified(unverifiedReason: budget_exceeded)를 돌려준다. event-analyzer는 재판정하지 않고 그대로 발행하며 event.manifest에 수를 싣는다. 완료 판정은 정상 진행된다. quality-service가 event.analyzed에서 사유별 검토 큐를 만들고, 화면은 "예산 초과로 판정하지 않은 이벤트 N건"을 표시한다. 예산이 복구되면 운영자가 보통의 REANALYZE를 돌린다. 이미 판정된 후보는 결과 캐시가 적중하므로 unverified였던 후보만 실제로 호출된다. 자동 재판정은 비용 폭주 위험 때문에 두지 않는다.

18. 환경·배포

18.2 인증

auth-service가 로그인과 토큰 발급을, api-gateway가 모든 요청의 토큰 검증을 맡는다(SPEC-001, 접근 토큰 계약, ADR-0004).

  • 접근 토큰은 JWT(ES256) 15분이고 브라우저는 메모리에만 둔다.
  • 재발급 토큰은 임의 문자열 14일, HttpOnly·Secure·SameSite 쿠키, DB에는 해시만 저장한다. 재발급마다 회전하고 이미 쓴 토큰이 다시 오면 같은 계열 전체를 폐기한다.
  • 역할은 USER(자기 소스), OPERATOR(재분석·활성 버전·검토·카메라 세션), ADMIN(사용자·프로필·카메라 관리)이다.
  • SSE 연결은 30초짜리 1회용 티켓으로 한다.
