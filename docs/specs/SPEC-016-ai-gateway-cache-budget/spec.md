# SPEC-016 ai-gateway 결과 캐시·예산·호출 한도

> 이 문서에는 **무엇을, 왜**만 쓴다. 클래스, 테이블, 라이브러리 같은 구현 방법은 각 레포의 plan.md에 쓴다.

## 1. 배경과 목적

ai-gateway는 모든 외부 모델 호출이 지나는 유일한 관문이다([아키텍처 개요](../../architecture/overview.md) "AI Gateway"). 유료 모델(VLM, 텍스트 임베딩)은 호출마다 비용이 들고, 공급자는 분당 요청·토큰 수를 제한한다. 지금은 같은 입력을 다시 보내도 매번 모델을 부르고, 비용과 호출 속도에 아무 제한이 없다.

이 spec은 처리 순서 "결과 캐시 → 예산 → 토큰 버킷 → Adapter"의 앞 세 단계를 더한다.

| 장치 | 막는 것 |
| --- | --- |
| 결과 캐시 | 재전달·재배치·재시도·같은 버전 재판정 job처럼 같은 입력을 다시 판정할 때 드는 비용과 지연. 같은 입력이 동시에 오면 한 번만 부른다. |
| 예산 | 재시도 루프, 잘못된 재처리 job, 호출 서비스의 버그 같은 사고로 외부 모델 비용이 폭주하는 것. 호출 서비스별·전체 하루 비용 한도를 둔다. |
| 토큰 버킷 | 여러 Pod가 공급자의 분당 한도를 넘어 429가 연쇄로 나는 것 |

예산은 시스템 안전장치이고 사용자에게 거는 제한이 아니다. 사용자 상한(영상 길이, 사용자별 일일 처리량, 정밀 검색·RAG 횟수)은 상품 규칙이라 사용자를 아는 media-service·search-service가 맡는다(overview "사전 견적·상한"). ai-gateway는 최종 사용자를 모르고 호출 서비스(`X-Caller`)만 안다.

캐시는 외부 모델을 실제로 부르는 경로에만 둔다. 질의 사전 해석(SPEC-012)과 ai-gateway 안의 인코더(SPEC-011)는 수 ms라 캐시를 조회하는 시간과 비슷하고 비용이 없다. 검색 결과 재사용(정밀 검색·RAG 결과)은 search-service가 표준 질의로 따로 저장한다.

예산을 넘으면 모델이 미설정일 때와 같은 결과를 돌려준다. 호출자는 이미 그 경로를 처리하므로 새로 처리할 것이 없다. Redis는 캐시 앞단·동시 호출 합치기·토큰 버킷에만 쓰고, Redis가 없어도 서비스는 계속 동작한다(overview "가용성").

## 2. 범위

### 포함

- 결과 캐시: `/v1/analyze`, `/v1/parse`의 LLM 보조 경로(`query_parse`), `/v1/embed`의 `embed_text`. 성공한 결과만 저장하고, 같은 입력이면 모델을 부르지 않고 저장된 결과를 돌려준다.
  - 입력이 같다는 기준: taskType, 모델, 프롬프트 버전(분류 체계 내용 포함), 입력 내용. `/v1/analyze`의 이미지는 경로가 아니라 내용으로 비교한다. `embed_text`는 문장마다 비교한다.
  - 영속 저장(DB)과 앞단 캐시(Redis). 보관 기간은 프로필 값이다.
  - 같은 입력이 여러 Pod에서 동시에 오면 한 번만 모델을 부른다.
  - `video.deleted`를 받으면 그 영상의 캐시를 지운다.
- 예산: 프로필의 모델별 토큰 단가로 예상 비용을 계산해 호출 전에 예약하고, 끝나면 실제 토큰으로 정산한다. 한도는 호출 서비스별 하루(UTC)와 전체 하루다. 넘으면 모델을 부르지 않고 미설정과 같은 결과를 돌려준다.
- 토큰 버킷: Adapter·모델마다 분당 요청 수·토큰 수 한도(프로필 값)를 모든 Pod가 함께 지킨다.
- Redis 장애 시 동작: 캐시는 DB만, 동시 호출 합치기는 생략, 토큰 버킷은 Pod별 한도로 대신한다.
- 호출 로그: 캐시 적중 여부, 예약·정산 비용, 새 상태 `budget_exceeded`
- 계약: `/v1/embed`의 예산 초과 오류 코드, 각 경로의 예산 초과·캐시 동작 설명
- docs overview: "AI Gateway" 처리 순서·호출 로그 상태, 다중 Pod 규칙의 ai-gateway 행을 이 spec에 맞춘다.

### 제외

- 단계 상향(`event_judge_escalate`로 다시 판정할지)의 판단: event-analyzer spec이 정한다([SPEC-009](../SPEC-009-ai-gateway-analyze/spec.md) 범위 제외와 같다). ai-gateway는 호출자가 고른 taskType을 그대로 처리한다.
- 사용자 상한(영상 길이, 일일 처리량, 정밀 검색·RAG 횟수): media-service·search-service
- 검색 결과 재사용(후보 검색, 정밀 검색, RAG 답변 저장): search-service
- 의미 유사도 캐시: 쓰지 않는다(overview "검색 결과 재사용").
- 호출자가 캐시를 건너뛰게 하는 요청 옵션: 평가 잡에 필요해지면 quality spec에서 더한다.
- 사전 해석, `embed_visual_text`·`embed_image`(자체 인코더)의 캐시·예산·토큰 버킷
- 예산 대시보드·알림(관측 지표는 호출 로그와 애플리케이션 로그로 남긴다)
- 인프라: 운영 Redis(ElastiCache)와 운영 프로필 값(사용자 지시 시 infra·gitops에서 한다)

## 3. 사용자 시나리오

이 기능의 사용자는 ai-gateway를 부르는 서비스(이하 호출자)와 운영자다.

### US-1 같은 판정을 다시 해도 모델을 다시 부르지 않음 (P1)

event-analyzer로서 재배치나 재시도로 같은 후보를 다시 판정할 때 같은 결과를 바로 받고 싶다. 왜냐하면 VLM 호출 한 번에 수 초와 비용이 들기 때문이다.

#### 인수 조건

- Given 성공한 `/v1/analyze` 결과가 있는 입력, When 같은 이미지 내용·입력 변수·taskType으로 다시 요청하면, Then 모델을 부르지 않고 같은 결과를 받는다.
- Given 프롬프트나 모델을 바꾼 프로필, When 같은 입력을 요청하면, Then 모델을 다시 부른다.
- Given 출력 검증에 실패했던 입력, When 다시 요청하면, Then 모델을 다시 부른다.

### US-2 같은 요청이 동시에 와도 한 번만 부름 (P2)

운영자로서 같은 입력이 여러 Pod에 동시에 와도 공급자 호출은 한 번이기를 원한다. 왜냐하면 재전달은 짧은 간격으로 몰려 오기 때문이다.

#### 인수 조건

- Given 같은 입력의 요청 두 개가 거의 동시에 서로 다른 Pod에 오면, When 둘 다 끝나면, Then 공급자 호출은 한 번이고 두 응답의 결과가 같다.

### US-3 비용 폭주를 막음 (P1)

운영자로서 버그나 잘못된 재처리 job이 있어도 하루 외부 모델 비용이 정한 금액을 넘지 않기를 원한다. 왜냐하면 유료 API 비용은 사고 뒤에 되돌릴 수 없기 때문이다.

#### 인수 조건

- Given 호출 서비스의 하루 한도를 다 쓴 상태, When 그 서비스가 `/v1/analyze`를 요청하면, Then 모델을 부르지 않고 `unverified` 결과를 200으로 받는다.
- Given 전체 하루 한도를 다 쓴 상태, When 어느 서비스든 모델 호출이 필요한 요청을 하면, Then 모델을 부르지 않는다.
- Given 한도를 다 쓴 상태, When 캐시에 있는 입력을 요청하면, Then 저장된 결과를 받는다.
- Given 다음 날(UTC), When 요청하면, Then 다시 모델을 부른다.

### US-4 공급자 한도 안에서 부름 (P2)

운영자로서 Pod 수를 늘려도 공급자의 분당 한도를 넘지 않기를 원한다. 왜냐하면 429가 나면 재시도가 몰려 장애가 커지기 때문이다.

#### 인수 조건

- Given 분당 요청 한도가 N인 모델, When 한 분 동안 여러 Pod에서 N보다 많은 요청이 오면, Then 공급자 호출은 분당 N 이하이고 나머지는 제한 시간 안에 차례를 얻지 못하면 일시 오류로 끝난다.

### US-5 Redis가 없어도 동작함 (P2)

운영자로서 Redis가 내려가도 분석·검색이 멈추지 않기를 원한다. 왜냐하면 Redis는 앞단 캐시일 뿐이기 때문이다.

#### 인수 조건

- Given Redis에 연결할 수 없는 상태, When 요청하면, Then DB 캐시와 예산은 그대로 동작하고 모델 호출은 Pod별 한도 안에서 이어진다.

### US-6 영상을 지우면 캐시도 지움 (P1)

영상 소유자로서 영상을 지우면 그 영상의 판정 결과가 ai-gateway에 남지 않기를 원한다. 왜냐하면 판정 결과에는 영상 내용 설명이 들어 있기 때문이다.

#### 인수 조건

- Given 캐시에 판정 결과가 있는 영상, When `video.deleted`를 받으면, Then 그 영상의 캐시가 DB와 Redis에서 지워지고 같은 입력은 다시 모델을 부른다.

### US-7 캐시 적중과 비용을 봄 (P3)

운영자로서 호출 서비스별 캐시 적중 비율과 쓴 비용을 알고 싶다. 왜냐하면 한도와 보관 기간을 정할 근거가 필요하기 때문이다.

#### 인수 조건

- Given 호출, When 끝나면, Then 호출 로그에 캐시 적중 여부와 예약·정산 비용이 남는다.

## 4. 요구사항

### 기능 요구사항 (EARS)

"캐시 대상 호출"은 `/v1/analyze`, `/v1/parse`의 LLM 보조(`query_parse`), `/v1/embed`의 `embed_text`다. "캐시 키"는 taskType, 프로필의 Adapter·모델, 프롬프트 버전(있으면), 입력 내용으로 만든다. `/v1/analyze`의 입력 내용은 이미지 바이트(보낸 순서대로)와 입력 변수, `query_parse`는 정규화한 검색 문장, `embed_text`는 문장 하나와 차원이다.

| ID | 요구사항 | 시나리오 |
| --- | --- | --- |
| R-1 | WHEN 캐시 대상 호출이 출력 검증을 통과해 성공하면, THE ai-gateway SHALL 그 결과를 캐시 키로 영속 저장소와 앞단 캐시에 저장한다. | US-1 |
| R-2 | WHEN 캐시 대상 호출의 캐시 키에 보관 기간(프로필 값) 안의 결과가 있으면, THE ai-gateway SHALL 모델을 부르지 않고 그 결과로 응답한다. 응답의 모델 ID·프롬프트 버전·분류 체계 버전은 저장한 값이고 호출 ID는 새 값이다. | US-1 |
| R-3 | IF 호출이 성공하지 않았으면(대체 결과, 출력 검증 실패, 모델 미설정, 공급자 오류, 예산 초과), THEN THE ai-gateway SHALL 그 결과를 캐시에 저장하지 않는다. | US-1 |
| R-4 | THE ai-gateway SHALL `/v1/analyze` 캐시 키에 이미지 저장소 경로가 아니라 이미지 내용을 쓴다. 같은 경로라도 내용이 다르면 다른 키다. | US-1 |
| R-5 | THE ai-gateway SHALL `embed_text` 캐시를 문장마다 찾아, 캐시에 없는 문장만 공급자에 보내고 결과를 입력 순서대로 합친다. | US-1 |
| R-6 | WHEN 앞단 캐시에 없고 영속 저장소에 있으면, THE ai-gateway SHALL 영속 저장소의 결과로 응답하고 앞단 캐시를 채운다. | US-1, US-5 |
| R-7 | WHILE 같은 캐시 키의 모델 호출이 다른 요청에서 진행 중이면, THE ai-gateway SHALL 모델을 부르지 않고 그 호출이 끝나기를 기다렸다가 저장된 결과로 응답한다. | US-2 |
| R-8 | IF R-7에서 기다린 호출이 성공하지 못했거나 그 taskType의 제한 시간(프로필 값) 안에 끝나지 않으면, THEN THE ai-gateway SHALL 직접 모델을 부른다. | US-2 |
| R-9 | WHEN `video.deleted`를 받으면, THE ai-gateway SHALL 그 영상 ID로 만든 `/v1/analyze` 캐시를 영속 저장소와 앞단 캐시에서 지운다(SPEC-009 R-20과 같은 소비). | US-6 |
| R-10 | WHEN 캐시에 없는 캐시 대상 호출이 모델을 부르기 전이면, THE ai-gateway SHALL 예상 비용(프로필의 모델 단가 × 예상 토큰)을 호출 서비스의 그날(UTC) 예산과 전체 그날 예산에서 함께 예약한다. | US-3 |
| R-11 | IF R-10에서 호출 서비스 예산이나 전체 예산의 남은 금액이 예상 비용보다 적으면, THEN THE ai-gateway SHALL 모델을 부르지 않고 예약하지 않으며, 모델이 미설정일 때와 같은 결과를 돌려준다(`/v1/analyze`는 200 `unverified`, `/v1/parse`는 200 `safe-fallback`, `embed_text`는 503 `AI_BUDGET_EXCEEDED`). 호출 로그에는 상태 `budget_exceeded`를 남긴다. | US-3 |
| R-12 | WHEN 예약한 모델 호출이 끝나면, THE ai-gateway SHALL 공급자가 알려 준 입력·출력 토큰으로 실제 비용을 계산해 예약을 정산한다. 공급자가 토큰 수를 알려 주지 않으면 예상 비용으로 정산한다. | US-3 |
| R-13 | IF 예약한 모델 호출을 공급자에 보내지 못했으면(연결 불가, R-16으로 차례를 얻지 못함), THEN THE ai-gateway SHALL 예약을 되돌린다. | US-3 |
| R-22 | IF 예약한 모델 호출을 보낸 뒤 토큰 수 없이 실패하면(제한 시간 초과, 공급자 오류), THEN THE ai-gateway SHALL 이미 과금됐을 수 있으므로 예상 비용으로 정산한다. | US-3 |
| R-14 | THE ai-gateway SHALL 캐시 적중, 단가가 없는 모델(프로필에 단가가 없는 로컬 모델·mock)의 호출은 비용 0으로 센다. | US-3 |
| R-15 | WHERE 프로필에 Adapter·모델의 분당 요청 수 또는 분당 토큰 수 한도가 있으면, THE ai-gateway SHALL 모든 Pod의 그 모델 호출을 합쳐 그 한도 안에서만 공급자를 부른다. | US-4 |
| R-16 | IF R-15의 한도 때문에 그 taskType의 제한 시간 안에 호출 차례를 얻지 못하면, THEN THE ai-gateway SHALL 공급자 일시 오류와 같은 결과로 끝내고(SPEC-009 R-18, SPEC-011 R-20, SPEC-012 R-13) 호출 로그에 상태 `unavailable`, 오류 코드 `AI_RATE_LIMITED`를 남긴다. | US-4 |
| R-17 | WHILE 앞단 캐시(Redis)에 연결할 수 없으면, THE ai-gateway SHALL 캐시는 영속 저장소만 쓰고, 동시 호출 합치기(R-7)는 하지 않으며, 분당 한도는 Pod별 한도(프로필 값)로 지키고, 경고 로그를 남긴다. 요청은 거절하지 않는다. | US-5 |
| R-18 | THE ai-gateway SHALL `/ready` 결과를 앞단 캐시 연결 상태와 상관없이 정한다. | US-5 |
| R-19 | WHEN 캐시 대상 호출이 끝나면, THE ai-gateway SHALL 호출 로그에 캐시 적중 여부, 예약 비용, 정산 비용을 남긴다. 캐시 적중이면 모델 원문은 남기지 않는다. | US-7 |
| R-20 | WHEN 기동하면, THE ai-gateway SHALL 캐시·예산·분당 한도 프로필(보관 기간, 모델 단가, 예상 토큰, 호출 서비스별·전체 하루 한도, 분당 한도, Pod별 한도)을 검증하고, 형식이 틀리거나 프로필에 없는 Adapter·모델·호출 서비스를 가리키면 기동에 실패한다. | US-3, US-4 |
| R-21 | WHERE 프로필에 호출 서비스의 하루 한도가 없으면, THE ai-gateway SHALL 그 서비스는 전체 하루 한도만 적용한다. | US-3 |

## 7. 성공 지표

- 로컬 compose에서 같은 `/v1/analyze` 요청을 두 번 보내면 두 번째는 모델 호출 없이 같은 결과를 받고, 호출 로그에 캐시 적중이 남는다.
- 호출 서비스 하루 한도를 작게 둔 프로필에서 한도를 넘으면 `unverified` 결과를 받고 공급자 호출이 없다.
- Redis 컨테이너를 멈춘 상태에서도 `/v1/analyze`·`/v1/parse`가 응답한다.
