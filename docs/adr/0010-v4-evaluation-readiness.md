# ADR-0010 v3 구조를 유지하고 평가·상태 변화·예측을 받칠 확장 자리(v4)를 더한다

> ⑦의 Prompt Registry 원본 위치와 ①의 클래스 대응표는 [ADR-0012](0012-prompt-registry-source.md)로 바뀌었다.

## 맥락

[ADR-0008](0008-industrial-safety-v3.md)이 산업안전 v3 구조(19개 배포 단위, 검색·이벤트 두 경로)를 정했다. 이후 팀이 단계 목표를 정했다.

| 단계 | 목표 | 쓰는 데이터 |
| --- | --- | --- |
| 1차 | 기본 탐지 성능 | 외부 bbox 정답(Construction Safety, Warehouse, Fire/Smoke) |
| 2차 | 영상 기반 위험 이벤트 평가 | 행동·장면 구간 라벨(Safe & Unsafe Behaviours, PhysicalAI-Event-Videos) |
| 3차 | 작업 전후 상태 변화 | 안전시설 제거·이동, 장비 방치, 미복구, 후속 위험 노출 |
| 이후 | 예측 | 확정 이벤트·위험 상태의 시간순 기록 |

설계 원본(루트 `references/검색·이벤트 VLM 아키텍처_v2.md`, 내용은 v4)은 v3 구조로 이 목표를 진행할 때 막히는 지점을 확인했다.

- 이벤트 유형·클래스가 코드와 DB enum에 있으면 유형을 하나 더할 때마다 여러 서비스 배포와 마이그레이션이 필요하다. 결과에 분류 체계·탐지 프로필 버전이 남지 않으면 단계별 평가 결과를 나중에 비교할 수 없다.
- 모델 가중치의 저장 규칙이 없어 어떤 파일이 어느 프로필에 쓰였는지 추적할 수 없다. 지금 ai-gateway 프로필은 가중치 키와 해시를 직접 적는다([SPEC-011](../specs/SPEC-011-ai-gateway-embed/spec.md) R-15).
- 이벤트 후보가 탐지기 클래스에서만 나온다. 2차 목표의 행동 라벨은 대응하는 클래스가 없어 후보가 0건이고 재현율이 0이다.
- 상태 변화 규칙이 Chunk Processor의 2분 청크 안에서만 동작한다. 청크는 병렬이라 앞 청크를 모른다. 청크·영상 경계를 넘는 제거·이동을 볼 수 없고, '장비 방치'·'이동'은 분류 체계에 없다.
- taskType이 코드에 묶여 있고, 프롬프트와 프로필을 이미지 빌드 때 넣는다. 지금 ai-gateway는 출력 검증은 계약의 JSON Schema로 하지만, 검증 실패 시 대체 결과와 mock 출력이 `event_judge` 전용 코드다. 프롬프트를 바꾸면 이미지를 다시 배포해야 한다.
- 예측 모델은 VLM이 아니라 작은 표 형태 모델이라 기존 Adapter에 들어가지 않고, GPU가 없어 CPU에서 돌아야 한다.
- 외부 데이터셋의 bbox·구간 라벨을 넣을 자리가 없다. Golden Set은 운영자가 검토 큐에서 만드는 이벤트 라벨만 가정한다.
- 처리 시간이 어디서 드는지 모른다. 서비스마다 로그로만 남기고, 큐 대기 시간은 어느 서비스 안에서도 잴 수 없다.
- 영상을 지우면 파생 데이터까지 모두 지워 예측 학습 데이터가 쌓이지 않는다.

## 결정 요인

- 모델·학습·데이터셋·프롬프트는 AI 담당자가, 서버 구조는 서버 담당자가 맡는다. 두 쪽 일정이 서로 묶이지 않아야 한다.
- v3로 이미 구현한 것(normalize, ai-gateway `/v1/analyze`·`/v1/embed`, media·auth·api-gateway)을 다시 만들지 않아야 한다.
- 다른 담당자 서비스(pipeline, chunk-processor 등)의 코드 변경을 최소로 한다. 특히 Pipeline 완료 판정은 `event.candidate`가 "청크당 정확히 1건"이라는 약속 위에 있다.
- GPU 노드가 없다.
- 개인정보는 영상·프레임·크롭에 있다. 블러 사본만 저장·전송하는 원칙은 유지해야 한다.

## 검토한 선택지

### 1. v3 유지, 필요할 때마다 개별 결정

- 장점: 지금 할 일이 없다.
- 단점: 단계 목표를 진행하면서 같은 막힘(유형 추가 배포, 후보 0건, 경계를 넘는 상태 변화)을 서비스마다 따로 풀게 된다. 평가 결과에 버전이 남지 않아 1·2차 결과를 비교할 수 없다.

### 2. v4를 새 구조로 보고 ADR-0008을 대체

- 장점: 결정이 한 문서에 모인다.
- 단점: v4는 v3의 서비스·경로·정직성 원칙을 그대로 둔다. 대체하면 바뀌지 않은 v3 결정(모델 교체 원칙, 원본 설계 수정점)을 다시 옮겨 적어야 하고, 무엇이 실제로 바뀌었는지 흐려진다.

### 3. ADR-0008을 유지하고 v4 확장 자리를 이 ADR로 더함

- 장점: 바뀐 것만 기록한다. 이미 구현한 서비스는 대부분 그대로 두고, 확장 자리만 계약·라이브러리·프로필로 만든다.
- 단점: 구조를 이해하려면 ADR 두 건을 함께 읽어야 한다. overview가 두 ADR의 내용을 합쳐 보여 줘야 한다.

### 프롬프트·프로필 전달 방식 (⑦의 세부 선택)

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| 지금처럼 이미지에 넣음 | 추가 장치가 없다. | 프롬프트를 바꿀 때마다 이미지 재빌드·배포가 필요하다. |
| gitops ConfigMap | Argo CD가 반영한다. | docs 계약과 gitops에 같은 내용이 두 벌 생긴다. ConfigMap 크기 상한(1MiB)이 있다. |
| 저장소 버전 경로에서 기동 시 받음 | 가중치(②)와 같은 규약·로더를 쓴다. 이미지 재빌드 없이 재기동만으로 바뀐다. 버전이 경로에 남아 결과와 연결된다. | 업로드 단계(CI)와 읽기 권한이 필요하다. 기동이 저장소에 기대게 된다. |

## 결정

**선택지 3**을 택한다. 프롬프트·프로필은 **저장소 버전 경로에서 기동할 때 받는다**. 이유: v3 결정과 구현을 유지하면서, 단계 목표가 막히는 자리만 서버 쪽에 미리 만들어 AI 담당자가 계약 파일과 저장소 업로드만으로 유형·모델·프롬프트를 바꿀 수 있게 한다.

| 번호 | 확장 자리 | 바뀌는 것 | 바뀌지 않는 것 |
| --- | --- | --- | --- |
| ① | 분류 체계·탐지 프로필을 데이터로 | 이벤트 유형·트리거 클래스·객체 종류를 `docs/contracts/taxonomy/`의 버전 파일에서 읽고 기동 시 검증한다. DB에는 문자열과 `taxonomy_version`으로 저장하고, 결과마다 분류 체계·탐지 프로필 버전을 기록한다. 탐지 프로필에 버전·학습 출처·체크섬을 더한다. 분류 체계 v2는 이벤트 유형 8종(`equipment_abandoned`, `object_moved` 추가)과 클래스 대응표 형식을 담는다. | 유형의 의미, 후보 → 판정 → 상태 전이 흐름 |
| ② | 모델 산출물 규약 | 모델 저장소에 `models/<종류>/<버전>/` 접두사와 `manifest.json`(체크섬·클래스·차원·학습 출처)을 둔다. 프로필은 manifest를 가리키고, 워커는 내려받아 체크섬을 확인한 뒤에만 `/ready`를 연다. AI 담당자는 이 접두사에만 쓰기 권한을 갖는다. | 가중치를 이미지에 넣지 않고 기동 시 받는 원칙, Shadow·Canary 절차 |
| ③ | 두 번째 후보 경로 | Frame Encoder가 구간 벡터를 프로필의 유형별 텍스트 프로토타입과 비교해 임계값을 넘는 구간을 `event.candidate.vector`로 발행한다. Event Analyzer는 두 토픽을 구독하고 판정 방식 `vector+vlm`을 기록한다. 이 토픽은 Pipeline 완료 판정에 넣지 않는다. | 기존 후보 경로, 완료 판정, Chunk Processor·Pipeline 코드 |
| ④ | 작업 세션 | Media에 `work_session`(현장·구역, 소스 목록과 역할 `before`·`during`·`after`)을 두고 `video.uploaded`에 `sessionId`·`role`을 싣는다. Aggregator는 세션의 직전 소스 최종 스냅샷을 초기 상태로 쓴다. | 세션 없는 영상은 한 영상 안에서만 상태를 잇는다. |
| ⑤ | 정적 객체 재고 비교 | `chunk.manifest`에 청크별 정적 객체 재고(클래스·위치·구역·처음·마지막 관측)를 싣는다. Aggregator가 재고를 시간순으로 비교해 제거·등장·이동·미복구 후보를 만들고, 전후 대표 프레임으로 `event_judge`·`state_compare`를 불러 판정한다. | 청크 안 상태 변화 규칙, Event Analyzer 경로, 완료 판정. 재고 비교는 완료 판정 뒤에 돈다. |
| ⑥ | 노출 지표 | 위험 상태마다 활성 시간·활성 중 진입 인원·누적 체류를 Aggregator가 계산해 `source.completed`에 싣고 Analysis가 저장한다. | 위험 상태의 활성·해소 전이 규칙 |
| ⑦ | AI Gateway 확장점 | taskType을 Prompt Registry 등록(프롬프트·출력 스키마·대체 결과·모델)만으로 추가한다. 프롬프트·분류 체계 묶음과 프로필은 저장소 버전 경로에서 기동 시 받고 체크섬을 확인한다(② 로더 공유). `predictor` Adapter(CPU에서 작은 모델 파일 실행)와 taskType `state_compare`·`risk_forecast` 자리를 둔다. | `/v1/analyze`·`/v1/embed`·`/v1/parse` 인터페이스, 블러 사본 규칙, 캐시·예산·출력 검증 순서 |
| ⑨ | Quality 데이터 틀 | 라벨 종류를 bbox 검출·시간 구간 이벤트·상태 변화 셋으로 둔다. 외부 데이터셋 가져오기(매니페스트 → Media 등록 + 라벨 적재 + 개발·평가 분할), 시간 구간 매칭 규칙(temporal IoU), 평가 실행 기록의 버전 고정(데이터셋·분류 체계·프로필·모델), 예측 학습용 특징 내보내기를 더한다. | Golden Set 버전 관리, 검토 큐, CI Gate, 정직성 원칙 |
| ⑩ | 처리 단계 측정 | 단계 ID 목록(`docs/contracts/stages/`)과 `StageTiming` 기록 형식을 계약으로 둔다. 이벤트 봉투에 `producedAt`을 더하고, 공통 메시징 라이브러리가 소비마다 큐 대기·처리 시간을 자동으로 잰다. 핸들러당 한 메시지로 `stage.timing`에 보내고 Quality가 적재·리포트한다. 성능 회귀 규칙(단계 p95가 기준선 대비 일정 비율 이상 느려지면 실패)을 CI Gate에 둔다. | 비즈니스 이벤트 payload와 처리 흐름 |

⑧ 파생 데이터 보존 등급은 개인정보와 동의 기준을 정해야 해서 별도 ADR로 결정한다.

## 결과

- 좋아지는 점:
  - AI 담당자가 유형·클래스·모델·프롬프트를 계약 파일 PR과 저장소 업로드만으로 바꿀 수 있어, 서버 배포와 일정이 묶이지 않는다.
  - 1·2·3차 평가 결과에 분류 체계·프로필·모델 버전이 남아 단계 사이 비교가 된다.
  - 행동 유형도 후보가 생기고(③), 청크·영상 경계를 넘는 상태 변화를 볼 수 있다(④⑤).
  - 처리 시간을 단계별로 나눠 보고, 모델 교체의 속도 영향을 정확도와 나란히 볼 수 있다(⑩).
- 감수할 점:
  - 계약 파일이 늘어난다(분류 체계 v2, 탐지 프로필·manifest 스키마, 단계 ID 목록, `StageTiming`, 새 토픽 2개).
  - ai-gateway 기동이 저장소(프롬프트·프로필·가중치)에 기댄다. 저장소를 읽지 못하면 `/ready`가 열리지 않는다.
  - 공통 메시징 라이브러리에 측정 코드가 들어가 모든 소비자가 영향을 받는다. 핸들러당 메시지 1건으로 묶어 부하를 줄인다.
  - `chunk.manifest` 재고 필드는 Chunk Processor 담당자가 채워야 ⑤가 동작한다.
- 후속 작업: [아키텍처 v4 전환 작업 목록](../architecture/legacy/v4-transition.md)에서 관리한다.
  - [아키텍처 v5](../architecture/architecture.md)·[서비스 카탈로그](../architecture/service-catalog.md) 갱신
  - 계약: 분류 체계 v2, manifest 스키마, 단계 ID 목록·`StageTiming`·봉투 `producedAt`, Media 세션 필드
  - ai: manifest 로더(SPEC-011 R-15·R-16·R-18 갱신), taskType 등록 방식과 프롬프트·프로필 받기, 결과의 `taxonomy_version`, `libs/messaging` 측정
  - backend: media 작업 세션·데이터셋 가져오기, `common-messaging` 측정
  - 파생 데이터 보존 등급 ADR
