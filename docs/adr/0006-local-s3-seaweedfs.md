# ADR-0006 로컬 개발과 테스트의 S3 대체 저장소로 SeaweedFS를 쓴다

## 맥락

운영에서는 영상 원본, 정규화 사본, 키프레임, 벡터 파일을 S3에 둔다. 로컬 compose와 Testcontainers 통합 테스트에서도 같은 S3 API를 쓰는 저장소가 필요하다. SPEC-003의 업로드 계약은 다음 S3 기능을 쓴다.

- 브라우저 POST 업로드 정책(SigV4)과 `content-length-range` 조건: 신고한 크기와 다른 파일을 저장소가 거절해야 한다(SPEC-003 R-2).
- 멀티파트 업로드: 조각별 서명 PUT 주소, 조각 합치기, 업로드 취소(R-3, R-8, R-13, R-20)
- path-style 주소, 크기 조회(HEAD), 접두사 단위 삭제

## 결정 요인

- 운영 S3와 같은 SDK·서명 방식으로 테스트할 수 있어야 한다. 로컬에서만 다른 코드 경로를 두지 않는다.
- 공식 컨테이너 이미지가 계속 배포되고 arm64(개발 머신)를 지원해야 한다.
- 로컬 메모리 예산 안에 들어가야 한다(아키텍처 개요의 로컬 목표 구성: 384MB).

## 검토한 선택지

### 1. SeaweedFS (단일 컨테이너 `server -s3`)

- 장점: 공식 이미지(`chrislusf/seaweedfs`)가 계속 배포되고 arm64를 지원한다. 4.48에서 POST 정책 업로드(크기가 다르면 400 `EntityTooLarge`), 멀티파트 업로드·합치기·취소, HEAD를 직접 확인했다(2026-11-02).
- 단점: POST 정책 서명을 검증하려면 접근 키(identity) 설정 파일이 있어야 한다. 버킷 이벤트 알림을 지원하지 않는다(업로드 완료는 클라이언트의 완료 요청만 쓰므로 영향 없음).

### 2. MinIO

- 장점: S3 호환성이 가장 널리 검증됐고 Testcontainers 모듈이 있다.
- 단점: 커뮤니티판의 공식 컨테이너 이미지 배포가 중단됐다.

### 3. LocalStack

- 장점: S3 외 AWS 서비스도 흉내 낸다.
- 단점: 필요한 것은 S3뿐이라 무겁다. 일부 기능과 최신 이미지는 계정·라이선스 정책이 바뀌어 왔다.

## 결정

**SeaweedFS**를 로컬 compose와 Testcontainers 통합 테스트의 S3 대체 저장소로 쓴다. 이유: 계약이 쓰는 S3 기능(POST 정책, 멀티파트)을 실제로 지원하는 것을 확인했고, 공식 이미지가 유지되며 가볍다. 운영은 계속 S3를 쓴다.

## 결과

- 좋아지는 점: 서비스 코드는 운영과 같은 AWS SDK와 서명 방식을 쓰고, 저장소 주소와 접근 키만 환경변수로 바꾼다.
- 감수할 점: 로컬·테스트 설정에 SeaweedFS 접근 키 설정 파일을 둔다(로컬 전용 공개 샘플 값). 브라우저 업로드를 위해 로컬 CORS 설정이 필요하다(frontend 업로드 화면 spec에서).
- 후속 작업: `local/docker-compose.yml`에 SeaweedFS와 버킷 생성 추가(SPEC-003 구현), 운영 S3 버킷·권한은 infra 레포에서
