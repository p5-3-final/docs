# ADR-0013 서비스 간 계약을 버전 릴리스로 배포하고 쓰는 쪽은 잠금 파일로 고정한다

## 맥락

레포 경계를 넘는 계약(OpenAPI, AsyncAPI, 이벤트 JSON Schema, 접근 토큰 형식, 분류 체계)의 원본은 docs 레포 `docs/contracts/`다. 이 계약을 쓰는 방식이 레포마다 다르다.

| 쓰는 곳 | 지금 방식 |
| --- | --- |
| ai·backend·frontend CI | 실행할 때마다 docs main을 checkout해 `CONTRACTS_DIR`로 넘긴다. |
| ai-gateway 이미지 | 빌드하는 순간의 docs main에서 분류 체계를 복사한다. |
| 로컬 개발 | 작업 공간의 `../../docs/contracts`를 읽는다. |

그래서 같은 커밋을 다시 빌드하거나 테스트해도 docs main이 바뀌었으면 결과가 달라진다. docs에서 계약을 바꾸면 관계없는 레포의 CI가 한꺼번에 깨지고, 그 사이 순서를 사람이 맞춰야 한다(ai #24 → docs #70). [ADR-0012](0012-prompt-registry-source.md)는 ai 레포에 분류 체계 사본을 두고 docs main과 같은지 검사하기로 했지만, 레포마다 사본과 검사가 따로 생기는 방식이라 관리 규칙이 하나로 모이지 않는다.

또 계약이 `docs/` 아래에 있어 사람이 읽는 문서의 일부처럼 보이고, 다른 레포에서는 `docs-repo/docs/contracts`처럼 경로에 docs가 두 번 들어간다.

## 결정 요인

- 같은 커밋은 언제 빌드해도 같은 계약으로 빌드·테스트돼야 한다.
- 모든 레포와 언어(Python, Java, TypeScript)에 같은 규칙 하나를 적용한다.
- spec과 계약은 지금처럼 한 PR에서 같이 바뀌어야 한다(SDD 흐름).
- docs 레포는 public이다. 인증 없이 받을 수 있는 배포 수단이면 infra가 필요 없다.

## 검토한 선택지

### 1. 레포마다 사본 + docs main과 같은지 검사 (ADR-0012 방식)

- 장점: 추가 장치가 없다.
- 단점: 레포마다 사본과 검사 스크립트가 생긴다. docs가 바뀌면 각 레포 CI가 한꺼번에 깨진다.

### 2. 버전 릴리스 + 잠금 파일

- 장점: "docs가 원본, 버전으로 릴리스, 쓰는 쪽은 잠금 파일로 고정"이 모든 레포에 같다. 재현된다. 계약을 올리는 것이 잠금 파일만 바꾸는 PR이 되고, 그 PR의 CI가 새 계약으로 검증한다.
- 단점: docs에 릴리스 단계가 생긴다. 계약을 바꾼 PR은 버전도 올려야 한다.

### 3. 언어별 패키지 배포

- 장점: 타입까지 생성돼 코드에서 쓰기 편하다.
- 단점: 언어마다 배포 파이프라인과 패키지 저장소 인증이 필요하다.

### 4. 런타임 조회 서비스(스키마 레지스트리)

- 장점: 중앙에서 한 번에 바꾼다.
- 단점: 새 서비스와 장애 지점이 생긴다. 이 규모에는 과하다.

### 폴더 위치와 이름

| 선택지 | 평가 |
| --- | --- |
| `docs/contracts/` 유지 | 바꿀 것이 없지만 문서의 일부처럼 보인다. |
| 루트 `contracts/` | 문서와 구분되지만 무엇 사이의 계약인지 이름에 드러나지 않는다. |
| 루트 `service-contracts/` | 서비스 사이의 인터페이스와 공용 값이라는 점이 이름에 드러난다. 릴리스 이름과 같다. |
| 별도 contracts 레포 | 레포 태그가 곧 버전이지만, spec과 계약이 다른 레포로 갈려 기능 하나에 PR이 둘이 된다. |

## 결정

**선택지 2**를 택하고, 계약 폴더는 docs 레포 루트의 **`service-contracts/`**로 옮긴다. 이유: 규칙 하나로 모든 레포가 같은 계약 버전을 재현하고, spec과 계약은 같은 레포·같은 PR에 남는다.

| 항목 | 규칙 |
| --- | --- |
| 원본 | docs 레포 `service-contracts/`(옮기기 전에는 `docs/contracts/`). 하위 폴더 `openapi/`, `asyncapi/`, `events/`, `auth/`, `taxonomy/`는 그대로 둔다. |
| 버전 | 원본 폴더의 `VERSION` 파일(SemVer). 계약을 바꾼 PR은 버전을 올린다. 필드·경로 추가는 minor, 설명만 바꾸면 patch, 하위호환 파괴는 major. PR CI가 버전을 올렸는지 검사한다. |
| 릴리스 | main에 머지되면 docs CI가 원본 폴더를 묶음(`service-contracts-<버전>.tar.gz`, 최상위 폴더 `service-contracts/`)과 SHA-256 파일로 만들어 GitHub Release `service-contracts-v<버전>`에 올린다. 같은 내용은 항상 같은 묶음이 되도록 파일 순서·시각·소유자를 고정한다. 한 번 올린 버전은 바꾸지 않는다. |
| 쓰는 쪽 | 레포 루트의 `service-contracts.lock`에 버전과 묶음 SHA-256을 적는다. CI는 받기 스크립트로 그 버전을 받아 체크섬을 확인하고 `CONTRACTS_DIR`로 넘긴다. 버전을 올릴 때는 잠금 파일만 바꾸는 PR을 연다. |
| 로컬 | 작업 공간의 원본 폴더를 바로 읽는다. 아직 머지하지 않은 계약을 시험하기 위해서다. 관문은 CI다. |
| 실행 중에 쓰는 계약 | 분류 체계처럼 서비스가 실행 중에 읽는 것은 잠금 파일의 버전을 이미지나 실행 설정 묶음에 넣는다. ai-gateway는 ai 레포의 Prompt Registry(ADR-0012)와 잠금 파일 버전의 분류 체계를 합쳐 쓴다. |

이 ADR은 ADR-0012의 "분류 체계 사본을 ai 레포에 두고 docs main과 같은지 검사한다"를 바꾼다. ai 레포는 분류 체계 사본을 두지 않고 잠금 파일 버전을 받는다. Prompt Registry 원본을 ai 레포에 두는 결정은 그대로다.

## 결과

- 좋아지는 점:
  - 같은 커밋은 같은 계약 버전으로 빌드·테스트된다. docs main이 바뀌어도 다른 레포 CI가 깨지지 않는다.
  - 계약을 올리는 시점을 쓰는 쪽이 정하고, 그 PR에서 새 계약으로 검증한다.
  - 결과와 이미지에 어느 계약 버전을 썼는지 남는다.
- 감수할 점:
  - 계약을 바꾼 PR은 `VERSION`도 올려야 한다.
  - 레포마다 받기 스크립트와 잠금 파일이 생긴다.
  - 로컬(작업 공간 원본)과 CI(잠금 파일 버전)가 다른 계약을 볼 수 있다. 로컬에서 통과해도 CI에서 실패할 수 있고, 그때는 잠금 파일을 올린다.
- 후속 작업: [아키텍처 v4 전환 작업 목록](../architecture/v4-transition.md)
  - docs: `VERSION`, 묶음 스크립트, 버전 검사·릴리스 워크플로, 첫 릴리스
  - ai·frontend·backend: 잠금 파일과 받기 스크립트, CI 전환. ai는 Prompt Registry 이전(ADR-0012)을 함께 한다.
  - docs: `docs/contracts/` → `service-contracts/` 이동과 링크·규칙 파일·각 레포 로컬 기본 경로 갱신
