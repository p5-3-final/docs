VLM 영상 분석 아키텍처 · 검색 경로와 이벤트 경로 (산업안전)

산업현장 CCTV 영상을 대상으로, VLM을 꼭 필요한 순간에만 부르는 두 경로로 구성합니다. 검색 경로는 영상을 10초 구간으로 잘라 구간마다 이미지 벡터를 만들어 두고, 사용자가 문장으로 장면을 요청하면 벡터로 후보를 찾아 그 시각으로 이동시키고 요청한 대상에 bbox를 그려 보여줍니다. 이벤트 경로는 탐지기가 지원을 선언한 산업안전 이벤트(쓰러짐, 화재 · 연기, 보호구 미착용, 물건 제거, 방호 미복구, 위험구역 접근)의 후보가 나왔을 때만 VLM으로 판정하고, 확정된 결과로 현장의 위험 상태(활성 · 해소)를 시간순으로 관리합니다. 두 경로는 한 번의 디코딩에서 갈라지고, 비싼 결과는 모두 DB에 남겨 재사용합니다.

v3는 연구용 프로토타입 vlm_project의 인코더 · 탐지기 선택, 판정 규칙, 정직성 원칙을 MSA 구조에 옮긴 판입니다. VLM만은 GPU 노드를 쓸 수 없어 로컬 Qwen3-VL 대신 v2대로 OpenAI를 운영에 쓰고, Qwen3-VL은 로컬 개발과 어댑터 선택지로 남깁니다.

v4 v4는 v3 구조를 그대로 둔 채, 팀의 세 단계 목표(1차 기본 탐지 성능, 2차 영상 기반 위험 이벤트 평가, 3차 작업 전후 상태 변화)와 그 뒤의 예측을 받칠 수 있도록 서버 쪽 준비 항목을 더한 판입니다. 모델 · 학습 · 데이터셋 · 프롬프트는 AI 담당자 몫이고, v4 항목은 서버 구조(계약, 토픽, 프로필 스키마, 저장 · 보존, 세션, 잡 틀, 단계별 처리 시간 측정)만 다룹니다.

달라진 점은 아래 "v4 변경: 평가 · 상태 변화 · 예측 준비" 절에 모았고, 본문에서 바뀐 표의 행과 문장에는 v4 표시와 주황색 띠를 붙였습니다. 표시가 없는 내용은 v3와 같습니다.

gRPC 내부 서비스 사이의 동기 호출(Search · 워커 → AI Gateway, Aggregator · Search → Analysis 내부 읽기, Chunk Processor → 추론 경계)은 HTTP(JSON)에서 gRPC로 바꿉니다. 상태 변경은 Kafka, 브라우저는 REST · SSE 그대로입니다.

달라진 점은 아래 "내부 통신 변경: 서비스 간 동기 호출을 gRPC로" 절에 모았고, 본문에서 바뀐 표의 행과 문장에는 gRPC 표시와 청록색 띠를 붙였습니다.

설계 원칙 (vlm_project에서 가져옴)

결과를 날조하지 않음모델이 설정되지 않았거나 가중치를 못 불러오면 명시적으로 실패합니다. 운영 코드에는 Mock 결과를 돌려주는 경로가 없습니다. Mock 어댑터는 CI · 단위 테스트 전용(TEST_DOUBLE:*)이고 운영 설정에서 선택할 수 없습니다.
탐지기가 능력을 선언이벤트 후보는 탐지기가 supported_events로 명시한 유형에서만 만듭니다. 범용 COCO 탐지기에 보호구 미착용을 선언하면 안 됩니다. 선언되지 않은 유형은 결과의 unsupported_events에 이유와 함께 남깁니다.
VLM 출력은 검증VLM 응답은 JSON 키 · 타입 · 상태 enum을 검사합니다. 근거가 부족하면 unknown · unverified · null을 허용하고, 그 값을 확정값으로 바꾸지 않습니다.
확정된 것만 상태에 반영위험 상태(활성 · 해소)와 상태 스냅샷은 confirmed 판정만 갱신합니다. events는 불변 이력, risk_state는 현재 상태로 분리합니다.
정확도를 주장하지 않음정답 세트가 없으면 지표를 None으로 둡니다. confidence · similarity를 정확도로 표시하지 않습니다. solution은 제안일 뿐이며 안전관리자의 최종 확인이 필요하다는 문구를 결과에 붙입니다.
결정적 ID구간 · 후보 · 트랙 · 결과 ID와 S3 경로는 uuid5(sourceId + 시각 + 규칙 + 트랙)처럼 결정적으로 만들어 재처리 중복을 흡수합니다.

왜 꼭 필요한가1차 목표의 산출물은 결국 '가중치 파일'입니다. 저장 규칙이 없으면 어떤 파일이 어느 프로필에 쓰였는지 추적이 안 되고, 잘못된 파일이 올라가도 서버가 모른 채 기동합니다. 규약이 있으면 '프로필에 버전 한 줄 바꿈 → Shadow → 전환'이 사람 손 없이 돌아갑니다.

가중치를 이미지에 넣지 않고 기동 시 내려받는 원칙, Shadow · Canary 절차.

③두 번째 후보 경로 event.candidate.vector2차

무엇이 바뀌나. Frame Encoder가 구간 벡터를 만든 직후, 프로필에 적힌 '유형별 텍스트 프로토타입'과 비교해 임계값을 넘는 구간을 후보로 event.candidate.vector에 발행합니다. Event Analyzer는 두 토픽을 구독하고 판정 방식을 vector+vlm으로 기록합니다. Pipeline 완료 판정(event.manifest 수)에는 넣지 않습니다. 프로토타입 문장과 임계값은 프로필 값이라 AI 담당자가 채웁니다.

왜 꼭 필요한가v3는 '탐지기가 클래스를 선언한 유형'만 후보를 냅니다. 2차 목표의 행동 데이터셋(Safe & Unsafe Behaviours 등)은 '사다리 위 불안전 자세'처럼 물체가 아니라 장면 · 행동 라벨이라 탐지기에 그런 클래스가 없고, 후보가 0건이면 재현율이 0이 됩니다. 구간 벡터는 이미 만들고 있으므로 비교 한 번은 CPU 비용뿐입니다. 별도 토픽으로 두는 이유는 event.candidate가 '청크당 정확히 1건'이라는 약속 위에 Pipeline 완료 판정이 서 있어서, 섞으면 완료 판정이 깨지기 때문입니다.
바뀌지 않는 것
기존 후보 경로, 완료 판정 규칙, VLM 판정 흐름. Chunk Processor · Pipeline은 변경 없음.
영향
docs ADR · AsyncAPI, Frame Encoder, Event Analyzer

⑤정적 객체 재고(inventory) 비교3차

⑨Quality 데이터 틀1 · 2 · 3차 평가 · 예측

⑩처리 단계 성능 측정전 단계 · 평가

수집과 리포트

  1. 라이브러리가 핸들러를 감싸 queue_wait · handle을 자동으로 재고, 핸들러 안의 stage() 블록이 세부 단계를 더한다. 핸들러 하나가 끝나면 그 안의 기록을 한 메시지로 묶어 stage.timing(키 sourceId)에 보낸다. 실패해도 측정은 남긴다.
  2. Quality가 stage.timing을 소비해 quality.stage_timing(월 단위 파티션)에 timingId로 upsert한다. 원본 기록은 90일, 일 단위 집계(단계별 p50 · p95 · 영상 1분당 시간 · 프로필 버전별)는 영구 보존한다.
  3. 리포트 세 가지: (a) 영상 하나의 단계 분해 타임라인(어느 단계가 얼마나, 큐 대기는 얼마나), (b) 단계별 p50 · p95 추이와 SLO 비교, (c) 프로필 · 모델 버전별 비교. (c)는 eval_run에 묶여 정확도 지표 옆에 속도가 같이 나온다.
  4. 기준선과 회귀 검사: 길이 · 해상도별로 고정한 벤치마크 영상 세트를 평가 잡으로 돌려 단계별 기준선을 만들고, CI Gate에 '단계 p95가 기준선 대비 N% 이상 느려지면 실패' 규칙을 둔다. Shadow 비교에도 같은 표를 쓴다.
  5. OpenTelemetry는 선택이다. 같은 라이브러리가 OTel span도 내보낼 수 있게 두되, 샘플링과 짧은 보존 때문에 영상별 완전한 분해와 버전 비교는 stage_timing 테이블이 맡는다. 로컬은 JSON 로그만 남긴다.

측정 오버헤드는 청크당 수십 건, 핸들러당 메시지 1건으로 묶으므로 무시할 수준이다. 큐 대기는 서로 다른 Pod의 시계를 비교하므로 브로커 timestamp(LogAppendTime)를 기준으로 하고, 시계 차이가 의심되면 queueWaitMs를 음수 그대로 남겨 지표에서 걸러낸다.

순서와 의존 관계

  1. ① → ② → ⑦이 기반입니다. 이 셋이 끝나면 AI 담당자는 계약 파일과 S3 업로드만으로 유형 · 모델 · 프롬프트를 바꿀 수 있고, 서버 PR 없이 돌아갑니다.
  2. ③, ⑤는 Chunk Processor · Pipeline 계약을 건드립니다. ADR과 계약 PR을 docs에 먼저 올리고, 머지된 계약을 기준으로 Frame Encoder · Event Analyzer · Aggregator 쪽만 구현합니다. 완료 판정에서 제외하는 설계라 Pipeline 코드 변경은 없습니다.
  3. ④ → ⑤ → ⑥은 Aggregator 안에서 순서대로 쌓입니다. ④가 없어도 ⑤는 한 영상 안에서 동작하므로 ⑤를 먼저 해도 됩니다.
  4. ⑧은 모든 DB 소유 서비스의 삭제 처리에 영향을 주므로 ADR을 일찍 내고 구현은 나중에 해도 됩니다.
  5. ⑨는 독립적입니다. AI 담당자가 1차 데이터셋을 들고 오는 시점에 맞춥니다.
  6. ⑩은 ①과 같이 가장 먼저 합니다. 공통 라이브러리에 들어가므로 뒤 항목들의 처리 시간을 처음부터 잴 수 있고, 1차 모델 비교 리포트에 속도가 함께 나옵니다.

내부 통신 변경: 서비스 간 동기 호출을 gRPC로 gRPC

내부 서비스 사이의 동기 호출을 HTTP(JSON)에서 gRPC로 바꿉니다. 바뀌는 것은 '동기 호출' 다섯 가지뿐입니다. 상태 변경을 Kafka 이벤트로만 전달하는 원칙, 브라우저가 쓰는 REST · SSE, 외부 AI 호출은 그대로입니다. 본문에서 바뀐 행과 문장에는 gRPC 표시를 붙였습니다.

gRPC 원칙은 하나입니다. 서비스 사이의 동기 호출은 gRPC, 상태 변경은 Kafka, 브라우저는 REST · SSE. 내부 동기 호출은 지금도 다섯 곳뿐이라 바꾸는 범위가 작고, 모두 계약(.proto)을 먼저 고친 뒤 양쪽 코드를 생성해서 맞춥니다.

왜 gRPC인가 (쉽게)

내부 호출이 다섯 곳뿐인데 왜 바꾸는지, 이득을 하나씩 풀어 씁니다. 핵심은 '서로 다른 언어로 만든 서비스가 같은 계약을 강제로 지키게 하는 것'입니다.

1계약이 곧 코드가 됩니다

지금은 OpenAPI 문서를 보고 Java(Search)와 Python(워커)이 각자 클라이언트를 손으로 씁니다. 필드 이름이나 타입이 어긋나도 실행해 보기 전엔 모릅니다. gRPC는 .proto 파일 하나에서 양쪽 서버 · 클라이언트 코드를 생성하므로, 계약과 다른 호출은 컴파일(Java) 또는 import(Python) 단계에서 걸립니다. 서비스를 여러 사람이 다른 언어로 만드는 이 프로젝트에 가장 큰 이득입니다.

2검색 왕복이 가벼워집니다

검색 한 번에 AI Gateway를 두세 번 부릅니다(질의 해석 → 질의 벡터 → 선택 재순위화). HTTP/1.1 + JSON은 호출마다 연결 · 헤더 · 텍스트 직렬화 비용을 냅니다. gRPC는 HTTP/2 연결 하나를 유지하며 여러 호출을 다중화하고 바이너리로 보내서, 작은 호출이 많은 검색 경로의 지연이 줄어듭니다. 벡터(512 float)도 JSON 문자열이 아니라 바이너리 배열로 갑니다.

3타임아웃이 호출 체인을 따라 전달됩니다

검색은 5~8초, RAG는 15초 안에 답해야 합니다. HTTP에서는 서비스마다 타임아웃을 따로 설정하고, 앞 서비스가 이미 포기한 요청을 뒤 서비스가 계속 처리하는 낭비가 생깁니다. gRPC의 데드라인은 호출자가 정한 '언제까지'가 메타데이터로 다음 서비스까지 전달되어, 남은 시간이 없으면 뒤 서비스가 즉시 멈춥니다.

4오류 의미가 언어와 무관하게 같습니다

예산 초과, 입력 거부, 서킷 열림을 HTTP 상태 코드(429 · 400 · 503)와 본문 형식으로 서비스마다 다르게 표현하고 있었습니다. gRPC 상태 코드(RESOURCE_EXHAUSTED, INVALID_ARGUMENT, UNAVAILABLE)는 Java · Python 라이브러리가 같은 예외로 바꿔 주므로 재시도 · 서킷 규칙을 한 번만 정하면 됩니다.

5호환성 검사를 도구가 합니다

OpenAPI는 oasdiff로 깨짐을 검사하듯, proto는 buf breaking이 필드 번호 재사용 · 타입 변경 같은 깨짐을 계약 PR에서 잡습니다. 계약 릴리스 규칙(VERSION · 잠금 파일)은 기존 그대로 씁니다.

6실시간(Phase 2)의 스트림 자리가 생깁니다

지금은 모두 단건 호출(unary)만 쓰지만, 같은 계약 형식으로 서버 스트리밍을 더할 수 있어 Phase 2의 프레임 · 알림 스트림을 다른 기술 없이 받칠 수 있습니다. 지금 만들지는 않습니다.

분할 단위와 연결 키

영상 하나가 어떻게 쪼개지고 각 조각이 어떤 키로 다시 이어지는지 정리합니다. 쪼개는 단위는 청크이고, 잇는 축은 sourceId + 분석 버전 + PTS(정규화 사본 기준 초) 세 가지입니다. 트랙만 청크 로컬 ID에서 최종 ID로 한 번 더 번역이 필요하고, 그 번역표를 Track Stitcher가 만듭니다.

분석 처리 흐름

단계마다 처리하는 서비스와 언어를 꼬리표로 붙였습니다. 초록은 Spring, 파랑은 Python 워커, 청록은 AI Gateway(Python), 회색은 사용자 · 플레이어입니다.

  1. 사용자→Media · Spring클라이언트가 /api/media에서 업로드 URL을 받습니다. 작은 파일은 presigned POST(크기 제한 포함), 큰 파일은 멀티파트 presigned URL입니다.
  2. Media · Spring/complete 요청과 S3 업로드 이벤트 중 먼저 온 신호가 source 상태를 UPLOADING → UPLOADED로 바꾸는 조건부 전이에 성공하고, 같은 트랜잭션에서 video.uploaded를 Outbox에 넣습니다. 나중에 온 신호는 아무것도 하지 않습니다.
  3. Normalize · PythonNormalize 워커가 ffprobe로 검증하고(video 스트림 · duration · fps 누락 시 REJECTED), 재생 정보를 앞으로 옮기거나 고정 fps로 다시 인코딩한 사본과 HLS 조각을 S3에 저장합니다. 영상 길이와 예상 처리 시간을 확정해 video.normalized를 발행합니다.
  4. Pipeline · SpringPipeline이 청크 계획을 세우고(기본 2분, 영상 길이에 따라 1~3분, 앞뒤 5초 겹침) 사용자별 → 소스별 → 전체 상한을 지키며 chunk.requested를 내보냅니다.
  5. Chunk Processor · PythonChunk Processor가 청크를 한 번만 디코딩하고 두 경로로 나눕니다. 검색 경로: 소유 범위 안에서 시작하는 10초 창 · 5초 간격 구간마다 균등 간격 프레임 4장을 뽑고, 얼굴 · 번호판을 블러 처리한 사본을 S3에 저장해 segment.ready로 목록을 보냅니다. 구간 사이 중복(지각 해시)이 심한 정적 구간은 플래그만 남기고 벡터는 모두 만듭니다(구간 수가 1시간에 720개로 작아 생략 이득이 없음). 이벤트 경로: 확장 범위로 YOLO26n · YOLO-pose · YOLOE(선언된 텍스트 클래스), ByteTrack을 돌리고, 이벤트 정의 목록의 규칙(트리거 클래스 · 최소 관측 수 · 전제 조건)에 맞고 시작 시각이 소유 범위 안에 있는 순간만 모아 청크당 한 건의 event.candidate(후보 목록, 0건 포함, 미지원 유형 목록 포함)로 보냅니다. 청크 안에서 끝난 트랙은 track.detected, 경계에 걸친 트랙은 chunk.boundary로 보내고, 검출 박스 · 크롭 · 크롭 외형 벡터 입력은 S3에 둡니다. 배회 · 체류처럼 시간이 기준인 규칙은 청크 안에서 판단하지 않고 트랙별 구역 진입 · 이탈 시각만 남깁니다. 마지막에 구간 수 · 후보 수 · 트랙 수를 담은 chunk.manifest를 발행합니다.
  6. Track Stitcher · PythonTrack Stitcher가 인접 청크의 경계 트랙을 IoU + 외형 벡터로 잇고, 같은 영상 안에서 화면을 떠났다 다시 나타난 트랙을 외형 벡터 유사도와 시간 간격 기준으로 다시 연결(Re-ID)한 뒤, 모든 청크가 끝나면 track.manifest를 발행합니다.
  7. Frame Encoder · Python→Search · SpringFrame Encoder가 구간마다 프레임 4장을 MobileCLIP2-S0으로 인코딩해 정규화 평균 벡터(512차원) 하나를 만들고, 트랙 대표 크롭 벡터도 만들어 벡터 파일을 S3에 저장해 segment.embedded를 발행합니다. Search가 파일을 읽어 COPY로 적재하고(halfvec, embedding_model, 차원, PTS, 대표 프레임 경로), 적재가 끝나면 segment.indexed를 발행합니다. embedding_model이나 차원이 활성 설정과 다르면 적재를 거부하고 오류로 남깁니다.
  8. Pipeline · SpringPipeline은 청크마다 manifest, Search의 적재 완료(segment.indexed), 이벤트 판정 완료를 진행 기록으로 남깁니다. 발행된 것이 아니라 적재가 끝난 신호를 셉니다. 기록할 때 job 행을 잠가 같은 영상의 신호를 하나씩 처리합니다.
  9. Event Analyzer · Python↔AI Gateway · PythonEvent Analyzer가 청크 후보 묶음 한 건을 받아 기다리는 단계 없이 바로 같은 트랙 · 같은 유형의 후보를 쿨다운(10초) 안에서 병합하고, 묶음 안의 후보를 제한된 수만큼 병렬로 판정합니다. 후보마다 전후 5초를 포함한 근거 프레임(박스 표시)을 모아 event_judge(terra)를 호출하고, 응답을 VLMAnalysis 스키마로 검증합니다. 키 누락 · 타입 오류면 unknown, 모델 미설정이면 unverified로 기록하고 후보를 버리지 않습니다. 애매하거나 severity high인 것만 event_judge_escalate(sol)로 다시 판정하고, 두 판정이 다르면 Quality 검토 큐에 넣습니다. event.analyzed와 청크별 event.manifest를 발행합니다.
  10. Analysis · Spring→Track Analyzer · Python→Embedding Worker · Python→Search · SpringAnalysis가 이벤트를 저장합니다. 관련 트랙은 청크 로컬 ID 참조로 함께 저장하고, Stitcher의 최종 트랙이 이미 와 있으면 바로, 아직이면 트랙이 도착할 때 연결합니다. 연결된 관련 트랙에 attribute.requested를 발행합니다. Track Analyzer가 속성(보호구 · 역할 · 장비)을 만들어 track.analyzed로 돌려주고, Embedding Worker가 이벤트 설명문과 트랙 속성을 임베딩해 Search 텍스트 인덱스에 넣습니다.
  11. Pipeline · Spring모든 청크의 벡터 적재(segment.indexed), 이벤트 판정, 트랙 manifest가 맞으면 Pipeline이 analysis.completed를 발행합니다. 트랙 속성 분석은 완료 조건에 넣지 않습니다.
  12. Aggregator · Python→Analysis · Spring→Notification · SpringAggregator가 Analysis의 내부 읽기 API로 영상의 이벤트 · 트랙 · 구역 · 구역 진입 · 이탈 시각을 한 번 읽습니다. (a) 청크 경계에서 나뉜 이벤트를 합치고, (b) 배회 · 체류 같은 시간 기준 규칙을 영상 전체 기준으로 판단해 템플릿 이벤트(VLM 없음)를 만들고, (c) 확정(confirmed) 이벤트만 시간순으로 훑어 구역별 상태 스냅샷(before_state → after_state)과 위험 상태 전이(risk_detected=true → 활성, 같은 유형 risk_detected=false → 해소)를 계산하고, (d) 타임라인과 텍스트 요약(source_summary)을 만듭니다. 이 결과를 모두 source.completed 한 건에 담아 보냅니다. Analysis는 자기가 저장한 이벤트 · 트랙 수가 manifest 수와 맞는지 확인한 뒤, 같은 트랜잭션에서 시간 규칙 이벤트 · 스냅샷 · 위험 상태 저장과 활성 버전 전환을 하고 Notification이 알립니다.
  13. 플레이어→Analysis · Spring→Track Analyzer · Python→Notification · Spring이벤트 타임라인에서 이벤트를 누르면 시작 2초 전으로 이동합니다. 위험 상태 패널은 활성 위험과 해소 이력을 보여줍니다. 화면을 클릭하면 Analysis가 (t, x, y)로 트랙을 찾아 속성이 있으면 바로, 없으면 클래스와 박스를 먼저 돌려주고 속성 분석을 요청한 뒤 SSE로 채웁니다. 객체에 질문을 입력하면 같은 경로로 object_question을 요청합니다.
  14. 사용자→Search · Spring사용자가 문장으로 장면을 요청하면 Search가 "텍스트 구간 탐색" 흐름으로, 질문을 던지면 "Video RAG" 흐름으로 처리합니다.

통신 원칙

외부 → 서비스모든 요청은 API Gateway를 거칩니다. Gateway가 JWKS로 JWT를 검증하고 사용자 ID와 역할을 헤더로 전달합니다. 클라이언트가 보낸 같은 이름의 헤더는 지웁니다.
서비스 ↔ 서비스 gRPC상태 변경은 Kafka 이벤트로만 전달합니다. 서비스끼리 동기 호출로 쓰기 요청을 하지 않습니다. 내부 읽기 전용 호출은 gRPC로 허용합니다(Aggregator → Analysis, Search → Analysis(RAG 근거)). Gateway → Auth JWKS만 표준 HTTP입니다. 읽기 호출은 호출하는 쪽이 없어도 제공하는 쪽이 동작하고, 응답이 없으면 호출하는 쪽은 재시도만 합니다.
동기 예외 gRPCSearch → AI Gateway만 Spring의 동기 호출입니다(질의 해석, 질의 벡터, 선택 재순위화, RAG 답변). gRPC 데드라인으로 검색 5~8초, RAG 15초를 호출 체인에 전달합니다. 검색은 데드라인을 넘기면 인코더 순위로 응답하고, 서킷이 열리면 재순위화 없이 응답합니다. RAG는 데드라인을 넘기면 답변 null과 근거만 돌려줍니다.
내부 동기 호출 프로토콜 gRPC내부 동기 호출은 모두 gRPC(HTTP/2, protobuf)입니다. 계약은 service-contracts/proto/, 데드라인 필수, 메타데이터에 traceparent와 호출자 토큰, headless Service + 클라이언트 round_robin. 세부 규칙은 "내부 통신 변경" 절에 있습니다.
시작 신호같은 작업을 시작시키는 신호가 여러 개여도 하나의 조건부 상태 전이로 모읍니다.
여러 Pod모든 서비스는 여러 Pod로 실행된다는 전제입니다. 청크는 행 잠금(FOR UPDATE SKIP LOCKED)으로 한 Pod만 가져가고, 주기 작업은 분산 락으로 한 Pod만 실행합니다.

대량 데이터구간 목록, 벡터, 검출 박스처럼 큰 데이터는 S3 파일로 두고 이벤트에는 경로와 개수만 싣습니다.

데이터 공유필터링과 권한 판단에 쓰는 최소 필드만 이벤트로 복제합니다. envelope에 ownerId를 싣습니다.

텍스트 구간 탐색 (검색 경로)

사용자가 "안전모를 안 쓴 작업자가 지게차 옆에 있는 장면"처럼 문장으로 요청하면, 분석 시점에 저장한 구간 벡터와 이벤트 텍스트에서 후보를 찾아 플레이어를 그 시각으로 이동시키고, 상위 구간에는 요청한 대상(작업자, 지게차)에 bbox를 그린 주석 클립을 붙입니다. 영상을 다시 분석하지 않습니다. VLM은 정밀 검색을 요청했을 때만 질의당 한 번 호출합니다.

처리 단계

검색은 Search(Spring)가 처음부터 끝까지 지휘하고, AI가 필요한 단계만 AI Gateway(Python)를 동기로 호출합니다.

  1. Search · Spring↔AI Gateway · Python질의 해석 (/v1/parse): 규칙 사전이 먼저 처리합니다. (a) QueryRouter가 시간 · 상태 표현("이후", "남은", "복구", "현재 위험", "작업 종료" 등)을 찾아 video_retrieval 또는 temporal_video_rag로 나눕니다. (b) QueryTargetResolver가 한국어 → 영어 시각 대상어 사전(안전모 미착용 → person without a hard hat, 지게차 → forklift, 연기 → smoke 등)으로 1~3개 대상어를 뽑습니다. 영문 질의면 불용어를 제거한 구문을 그대로 씁니다. 사전에 없으면 LLM query_parse(luna)로 보조하고, 그래도 없으면 person으로 제한합니다. 출력은 표준 질의(route, targets, event_types, 속성 enum, 시간 조건, 영어 검색 문장, method, explanation)이고, method(industrial-rule · english-phrase · llm · safe-fallback)를 결과에 표시합니다.
  2. Search · Spring재사용 확인: 표준 질의 키로 저장된 결과가 있으면 바로 돌려줍니다.
  3. Search · Spring라우팅: temporal_video_rag면 Video RAG 흐름으로 넘깁니다. video_retrieval은 이벤트 유형 · 속성이 잡히면 텍스트 인덱스도 함께, 아니면 시각 인덱스만 봅니다.
  4. AI Gateway · Python→Search · Spring시각 검색: 영어 검색 문장을 MobileCLIP2 텍스트 인코더로 벡터화해(embed_visual_text) 활성 버전 · 권한 범위 안의 구간 벡터에서 top-50을 찾습니다. 구간 하나가 10초 장면이라 별도 병합은 없고, 5초 겹치는 인접 구간은 점수 높은 쪽만 남깁니다.
  5. AI Gateway · Python→Search · Spring텍스트 검색: 질의 텍스트 벡터(embed_text)와 pg_trgm 키워드 검색을 RRF로 합치고, 이벤트 유형 · 속성 · 시간 조건은 필터로 적용합니다.
  6. Search · Spring↔AI Gateway · Python정밀 검색 (선택): 요청에 precise=true가 있을 때만 상위 10개 구간의 대표 프레임과 질의를 segment_rerank(terra)로 한 번에 보내 구간마다 일치 여부 · 점수 · 짧은 근거를 받습니다. 기준 점수보다 낮으면 "찾지 못함"으로 표시합니다. 기본 검색은 이 단계를 건너뜁니다.
  7. Search · Spring→플레이어결합 · 이동: 시각 결과와 텍스트 결과를 RRF로 합치고, 결과마다 이동 시각(시작 2초 전), 유사도 점수, 사용한 인코더 · 해석 방법을 돌려줍니다. 점수는 "유사도"로만 표시하고 정확도로 표시하지 않습니다.
  8. Search · Spring→Grounding Worker · Pythonbbox 주석 요청: 상위 3개 구간과 대상어로 grounding.requested를 발행합니다. 주석 클립이 이미 있으면(groundingId 일치) 경로만 돌려주고 발행하지 않습니다. 완료되면 grounding.completed → Notification SSE로 클립 경로가 도착합니다.
  9. Search · Spring→Embedding Worker · Python저장: 결과, (정밀 검색 시) 재순위화 판정, 주석 클립 경로를 DB에 저장하고, 신뢰도 높은 판정은 구간 주석으로 남겨 segment.annotated를 발행합니다.

이미지로 장면 찾기: POST /api/search/moments/by-image로 이미지를 올리면 AI Gateway /v1/embed(이미지 모드, MobileCLIP2 이미지 타워)로 벡터를 만들고 구간 벡터와 트랙 크롭 벡터 양쪽에서 찾습니다. 같은 인코더라 추가 인덱스가 없습니다.

Video RAG (질문 답변)

GET /api/search/sources/{id}/answer?q=로 "작업이 끝난 뒤 남은 위험은?" 같은 질문을 받으면 Search가 근거를 모으고 VLM이 근거만으로 답합니다.

단계서비스내용
1Search질의 해석(검색과 같음). route가 video_retrieval이어도 이 엔드포인트로 왔으면 RAG로 처리
2Search시각 검색 top-k(기본 5)로 근거 구간을 찾고 대표 프레임 경로를 모음

RAG 답변에는 "모델이 생성한 답변이며 안전관리자의 확인이 필요합니다" 문구를 항상 붙입니다. 객체 자유 질문(object_question)은 화면 클릭 경로에서 Track Analyzer가 같은 모델로 처리하고 결과를 Analysis가 저장합니다.

검색 결과 재사용

비싼 결과는 DB에 영구 저장하고 Redis는 앞단 캐시로만 씁니다. 키는 원문이 아니라 규칙 사전이 만든 표준 질의로 잡아 표현 차이("찾아줘", 조사)를 흡수합니다. 규칙 사전은 결정적이라 같은 문장에 항상 같은 키가 나옵니다. LLM 보조로 해석된 질의는 temperature 0과 모델 스냅샷 고정으로 재현성을 맞추고, 키에 해석 방법과 사전 버전을 포함합니다. 의미 유사도 캐시는 쓰지 않습니다.

여러 Pod 운영 원칙

모든 서비스는 여러 Pod로 실행된다는 전제로 설계합니다. Pod 메모리에는 공유 상태를 두지 않고, 같은 일을 두 Pod가 동시에 하지 않도록 아래 장치를 둡니다.

공통 규칙내용
상태 위치공유 상태는 DB · Redis · S3에만 둡니다. Pod 메모리는 캐시와 묶음 처리 버퍼, 로드한 모델로만 씁니다.
중복 실행 방지조건부 상태 전이, FOR UPDATE SKIP LOCKED, Redis 원자 연산(SET NX · Lua) 중 하나로 한 Pod만 성공하게 합니다.
멱등구간 · 후보 · 트랙 · 결과 · 주석 ID와 S3 경로는 결정적으로 만듭니다. 소비자는 eventId로 중복을 흡수하고, 일괄 적재(Analysis Loader · Search)는 임시 테이블에 COPY한 뒤 고유 키로 upsert합니다.
모델 로딩워커와 AI Gateway는 기동할 때 모델을 한 번 로드하고 /ready는 로드가 끝난 뒤에만 200을 돌려줍니다(vlm_project의 지연 로딩은 쓰지 않음). 가중치를 못 불러오면 기동 실패로 두고 Mock으로 넘어가지 않습니다.
Outbox 발행기Spring 서비스의 각 Pod가 FOR UPDATE SKIP LOCKED로 Outbox 행을 집계 단위(sourceId)로 묶어 가져가 발행합니다.
종료 신호SIGTERM이 오면 진행 중 작업을 중단하고 커밋하지 않은 채 소비 그룹에서 나갑니다. 재처리는 결정적 ID로 흡수됩니다.
주기 작업타임아웃 처리, 완료 점검기, 정리 작업은 분산 락(ShedLock 등)으로 한 Pod만 실행합니다.
Kafka 파티션토픽별 파티션 수를 소비 그룹의 최대 Pod 수 이상으로 잡고, KEDA · HPA 최대 Pod 수를 파티션 수에 맞춥니다. 재배치는 cooperative-sticky를 씁니다.
긴 처리Chunk Processor · Normalize · Event Analyzer · Grounding Worker는 pause/resume으로 처리합니다. max.poll.interval.ms는 약 10분, 처리 시간 감시로 기준을 넘긴 작업은 중단 · 실패 처리합니다.
커넥션 · 메모리Spring 커넥션 풀 크기 × 최대 Pod 수의 합을 RDS 최대 커넥션 안에 둡니다. Frame Encoder · AI Gateway(MobileCLIP2), Chunk Processor · Grounding Worker(YOLO 계열)는 Pod마다 모델을 올리므로 최대 Pod 수 × 모델 메모리를 노드 용량에 반영합니다.
서비스장치
Pipeline 완료 판정job 행을 FOR UPDATE로 잠근 트랜잭션 안에서 진행 기록 삽입, 개수 비교, 조건부 전이, Outbox 삽입을 한 번에 합니다. 세는 신호는 적재 완료(segment.indexed, event.manifest, track.manifest)입니다.
Pipeline 청크 분배스케줄러 틱은 분산 락으로 한 Pod만 실행합니다.

Notification · Authv2와 같습니다(Redis pub/sub + Stream 재전송, Refresh 회전 조건부 갱신, SSE 티켓 GETDEL).

인증 (자체 JWT + 외부 발급자)

Auth Service가 로그인과 토큰 발급을 맡고, API Gateway가 모든 요청의 토큰을 검증합니다. 외부 발급자(OIDC, 예: 회사 SSO · Google)로 로그인하면 Auth가 외부 ID를 external_identity로 연결하고 자체 JWT를 발급합니다. Gateway와 도메인 서비스는 발급 경로를 구분하지 않습니다.

VLM과 텍스트 임베딩은 로컬에서 OpenAI를 쓰지 않고 Mac 호스트의 Ollama(Qwen3-VL, 임베딩 모델)로 대체합니다. 컨테이너 안의 AI Gateway는 openai_compatible 어댑터로 호스트 Ollama를 호출합니다. 로컬 판정 · 재순위화 결과는 운영과 다르므로 품질 판단은 Golden Set 평가(운영 모델)로만 합니다.

오탐 · 미탐 검증 루프 (Quality Service · MVP)

Golden Set은 확정 버전을 S3에, 작업 중인 라벨과 평가 결과를 Quality DB에 둡니다. 이벤트 라벨(6종 + other, 근거 프레임 포함)과 (질의, 정답 구간) 세트를 함께 관리하고, 영상 단위로 개발 세트와 평가 세트로 나눕니다. 프롬프트 수정, 경계값, 정밀 검색 K, YOLOE 클래스 구성 같은 조정은 개발 세트로만 하고, CI Gate와 최종 보고는 평가 세트로만 합니다. 정답이 없는 항목은 None으로 두고, 운영 화면에는 Golden Set으로 잰 지표만 표시합니다.
