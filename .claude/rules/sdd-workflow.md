# SDD 워크플로 세부 규칙

## 문서 배치 (하이브리드)

| 문서 | 위치 | 이유 |
| --- | --- | --- |
| 프로젝트 원칙, PRD, 아키텍처, ADR | 루트 `docs/` | 전 레포 공통 |
| spec.md (무엇·왜) | 루트 `docs/specs/SPEC-NNN-<slug>/` | 한 기능이 여러 레포에 걸치므로 원본은 한 곳에 둔다 |
| OpenAPI / AsyncAPI 계약 | 루트 `docs/contracts/` | 생산자와 소비자가 같은 원본을 본다 |
| plan.md, tasks.md (어떻게) | 각 레포 `specs/SPEC-NNN-<slug>/` | 구현 세부는 코드와 같은 PR에서 리뷰한다 |

한 SPEC이 backend와 frontend에 걸치면 plan과 tasks는 각 레포에 하나씩 만들고, spec은 루트에 하나만 둔다.

## spec 상태 전이

`Draft` → `Review` → `Approved` → `Implementing` → `Done`. 대체되면 `Superseded`가 된다.

- `Draft`: 작성 중. `[NEEDS CLARIFICATION]`이 남아 있어도 된다.
- `Review`: docs 레포에 PR을 연 상태. 미결 사항이 없어야 한다.
- `Approved`: 리뷰 승인을 받은 상태. 승인 후 머지하기 전에 같은 PR에서 status를 `Approved`로 바꾸고 머지한다. 머지된 뒤부터 plan을 작성할 수 있다.
- `Implementing`: 첫 구현 PR이 열린 상태
- `Done`: 모든 요구사항의 테스트가 통과하고 배포까지 끝난 상태
- 상태를 바꿀 때마다 frontmatter의 `updated`와 `docs/specs/README.md` 목록을 같이 갱신한다.

## spec 작성 원칙

- spec에는 **무엇을, 왜**만 쓴다. 클래스, 테이블, 라이브러리 같은 구현 방법은 plan에 쓴다.
- 기능 요구사항은 모두 EARS 문법으로 쓴다. 문법은 `.claude/rules/docs-writing.md`를 참고한다.
- 요구사항 하나에는 검증 가능한 조건을 하나만 담는다. "빠르게", "적절히", "등" 같은 모호한 표현은 쓰지 않는다.
- 사용자 시나리오는 우선순위(P1/P2/P3)를 매긴다. P1 시나리오만으로도 독립적으로 시연할 수 있어야 한다.
- 모르는 것은 추측하지 않고 `[NEEDS CLARIFICATION: 질문]`으로 표시한다.

## plan 작성 원칙

- 시작하기 전에 spec이 `Approved`인지 확인한다. 아니면 멈추고 사용자에게 알린다.
- `원칙 점검` 섹션에서 `docs/principles.md`의 각 원칙을 지켰는지 확인한다. 위반이 있으면 그 이유를 쓰거나 설계를 바꾼다.
- 이 레포가 맡는 요구사항 ID를 전부 나열하고, 각 요구사항을 어떤 테스트로 검증할지 매핑한다.
- 대안을 비교해서 결정한 것 중 다른 레포에 영향을 주거나 되돌리기 어려운 것은 ADR로 승격한다.

## tasks 작성 원칙

- 태스크 하나는 커밋 하나에서 PR 하나 사이의 크기로 잡는다. 대략 반나절 이하가 기준이다.
- 태스크 하나는 요구사항 하나의 TDD 사이클(실패하는 테스트 → 구현 → 정리)이다. 테스트만 있는 태스크를 따로 만들지 않는다. 실패하는 테스트만 든 커밋이 생기면 CI가 깨지기 때문이다.
- 각 태스크에는 담당하는 요구사항 ID와 수정할 파일 경로를 적는다.
- 서로 의존하지 않는 태스크에는 `[P]` 표시를 붙인다.

## 추적성

요구사항부터 테스트까지 ID로 연결한다. 연결 형식은 루트 AGENTS.md "테스트 우선 개발 (TDD)"의 추적성 항목을 따른다.

## 구현 중 spec과 달라질 때

1. 코드를 계속 짜지 말고 멈춘다.
2. 사용자에게 차이를 알린다.
3. spec이나 계약을 먼저 고치는 PR을 docs 레포에 연다. 사소하면 같은 작업 흐름 안에서 처리해도 된다.
4. 갱신된 spec을 기준으로 plan과 tasks를 고친 뒤 구현을 재개한다.
